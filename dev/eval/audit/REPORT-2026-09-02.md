## 1. Summary

This audit measured how well engram's recall→act→learn loop actually worked across **150 real,
LLM-judged moments**, sampled from **568 mechanically-extracted transcript records** across **7
repositories** (main-agent and subagent transcripts, Claude Code sessions on Joe's own machine,
**2026-07-22 through 2026-09-01** — corrected here; an earlier draft mistakenly quoted the *vault's*
git-commit history range, 2026-06-02 through 2026-08-29, which is a different thing, see §8g). The
568-record full corpus technically spans an 8th project directory too (the audit's own working
session, `-Users-joe-repos-personal-engram-dev-eval-audit`, 2 of the 568 records) — that directory
was never eligible for sampling (it's the audit's own build activity, not real prior work being
measured), so the "7 repositories" figure describes the 150-moment sample specifically, not the
raw 568-record count. Of the 150 moments: 72
success, 27 failure, 17 rework, 28 dispatch, 6 correction (`scorecard-main.json`
`meta.moment_type_counts`).

The audit exists to answer one question for #739: **should Phase 2 proceed?** Per design.md
decision D-G and `specs/memory-loop-audit/spec.md`'s go/no-go requirement, Joe explicitly declined
to pre-commit numeric green/yellow/red thresholds for this decision (2026-09-01) — there is no
formula the numbers below get mechanically read off. Instead, **this report is the input to a
live, critical joint review between Joe and the agent**, at this same gate, informed by the full
context of what the numbers show, their DERIVED/ESTIMATE labeling, and the honest gaps documented
in §8. The go/no-go decision itself is task 6.3, after this report is presented.

## 5. The Fork-Context Judgment Fix

Mid-audit, a real gap was found and fixed in `audit_moments.py`'s `judge_moment()`: for fork-role
moments, the judge originally had no way to answer "was the surfaced memory followed?" because it
never actually saw the content the fork inherited from its parent — design.md D-E credits a fork
as "surfaced=true" purely structurally (a fork always inherits its parent's full conversation), but
the judge was never given that inherited content to check against. The fix resolves and injects the
real inherited-memory context before judging.

**What was measured:** 18 previously-detected fork-role moments were re-scored with real,
billed `claude -p --model sonnet` calls (`rescore_fork_followed.py`), reported at **$9.99 real
cost** (the script's own summed `total_cost_usd` from 18 real API calls, printed at run time but
not persisted to any file — plausible given the call count and model, but not independently
re-derivable from a static artifact). One rescored moment also had its `failure_category` flip from
`nothing_could_have_caught_it` to `fixable` as a side effect (`rescore_fork_followed.py` re-judges
the full record, not just `followed` — `agent-ad3f5d4aa55408741.jsonl#32`); this is already reflected
in every count elsewhere in this report (§4, §6, PROPOSALS.md's original 20-moment universe — since
extended to 49, see §6), disclosed here for provenance. The result (`results/rescore-fork-followed.jsonl`, verified by direct read):

- **2/18 became a real "yes" verdict** (the memory was genuinely there and followed).
- **16/18 remained null.** The judge's structured output has no free-text reasoning field, so "why"
  can't be read off the JSON alone — I hand-read the actual inherited content against each moment's
  own description for all 16 (quoting both below). **12/16 show a clear topical mismatch** — e.g.
  moment `agent-a5e3cc9e58c463d77.jsonl#5` ("Fork successfully executes its minimal directive...
  demonstrating the dispatch-while-backgrounded pattern worked") inherited only isolation/eval-design/
  vault-graph notes from an earlier, unrelated part of the same session; the 5 `agent-a8ce598d...`
  and 6 `agent-a81b80335...` moments (a file-read-size-limit retry sequence) all inherited the same
  two notes about "don't invent missing inputs" / "enumerate before probing" — generic enough to be
  a stretch either way, but not a clear match to a mechanical retry loop. For these 12, "topically
  unrelated" is a defensible read of the null. **The remaining 4/16** inherited more plausibly
  on-topic content and still got no `followed` verdict — `agent-a6493eb381d2089cc.jsonl#22/#24`
  inherited notes squarely about recall/memory-routing design while themselves being about writing
  recall/memory-routing issue proposals (a real thematic match); `#18` and `agent-ad3f5d4aa55408741.jsonl#32`
  are murkier calls (`#32`: "stop rather than invent" notes vs. a moment about inventing a wrong
  Luhmann ID — plausibly related) — but both `#18` and `#32` also have `search_targeted_right_thing`
  rendered `true` in the scored corpus, meaning the judge *did* engage with them on that separate
  question without resolving `followed` either way (**correction from an earlier draft, which
  misquoted `#32`'s value as `false` — that `false` came from the fork-context-fix's discarded
  rescore judgment, never merged into the scored corpus; the actual, scored value is `true`**). So
  the fix's real yield is smaller and messier than "informed vs. uninformed null": roughly 12/16
  look like defensible non-answers on this data, and 4/16 look more like a real judgment gap the
  fix didn't close.

**The takeaway is two-part, not one** (full numbers above; not repeated here — see §8f for the
Limits-section cross-reference):

1. D-E's blanket "any fork = surfaced=true" rule may over-credit structural availability over
   topical relevance, for the majority of this fix's remaining nulls.
2. A smaller remainder looked like a genuine, separate `judge_moment()` judgment-quality gap
   (on-topic content, still no verdict), unrelated to D-E's scoping.

**Followed-nulls closeout (2026-09-04, Joe-directed after his third unasked-null catch):** all
remaining bare F5 nulls were resolved for real. The 19 non-dispatch nulls — the 16 fork moments
above PLUS 3 non-fork moments with real recalls that the fork-scoped fix had missed (the fix's
target population had been derived from the diagnosis's exemplar, fork moments, instead of from
the symptom, all followed-nulls) — were re-asked with a direct question whose options include an
explicit `not_applicable` (a bare null is no longer a permitted answer). Result
(`rejudge-followed-nulls.jsonl`, one-sentence rationale each, $9.78, independently verified):
**1 became a real "yes"** (`agent-a6493eb381d2089cc.jsonl#24` — the strongest of the flagged
on-topic moments; the judge genuinely discriminated, giving its off-content siblings in the same
transcript explicit not-applicables) and **18 explicit `judged_not_applicable`**. The 5
dispatch-type nulls were mechanically labeled `not_applicable_dispatch_moment` (design: D1
measures dispatch moments; "followed" never applied). **Zero bare nulls remain in F5** — every
one of the 50 surfaced moments now carries either a verdict or a recorded reason
(`finding_side.followed_null_reason`).

## 5b. The Chunk-Index Recovery (2026-09-03/04)

A second during-gate finding — this one about the audit's own data-loss claims, and itself
dogfooding evidence for #739. Two places in this audit originally declared retention-deleted
source data unrecoverable:

1. **10 of the category-rescope's 67 target moments** (§8e), whose transcripts Claude Code
   session retention had deleted between the original run and the rescope
   (`rejudge-failure-category.jsonl` records them as skipped, "transcript deleted by retention").
2. **The 2 genuine D1 dispatches** whose parent main-session transcripts were gone (§4's
   raw-view limitation) — and by recovery time their child subagent transcripts were gone too.

Joe pointed at engram's own **append-only chunk index** (`~/.local/share/engram/chunks` — the
stripped-transcript layer behind the auto-ingested vector space) as a retention fallback. **All
claimed-lost sources were recovered from it:**

- All 10 rescope moments had surviving chunk content, and 9 of the 10 proved judgeable from it
  (`rejudge-failure-category-from-chunks.jsonl`): 9 judged (judge self-reported the chunk context
  sufficient), 1 honestly nulled because the judge self-reported the surviving context was
  insufficient (`failure_category_provenance: 'rejudge-chunks-insufficient-context'`,
  `agent-ac2925d5bb0aa269d.jsonl#35`) — an honest null, not a forced verdict.
- Both D1 dispatches were reconstructed (`results/handoff-gap-chunk-recovery.json`,
  independently verified): dispatch prompts **verbatim** from the child transcripts' chunks
  (identity-checked against each moment's description), pre-dispatch recall candidates
  **verbatim** from the parent transcripts' chunks.

Every chunk-derived judgment carries distinct provenance (`judged_from='chunks'` /
`failure_category_provenance='rejudge-chunks'`) plus the self-reported sufficiency flag — chunk
text is stripped and truncates long tool arguments/outputs, so these judgments are lower-fidelity
than raw-transcript ones (see §4's FLOOR caveat, and caveat (d): one 'sufficient' self-report's
load-bearing detail was in fact chunk-truncated).

**Why this matters beyond the recovered numbers:** the audit initially wrote this data off as
gone; the memory system's own raw layer outlived the host's transcript retention, and engram
itself is what got the data back. For the #739 discussion, the memory-loop audit is itself a

**The 5 proposed vault notes** (one line each — full proposed content is in `PROPOSALS.md`):

1. **safe-read-chunk-sizing** — after a Read/Bash size- or token-limit error, compute a
   guaranteed-under-budget chunk size from the error's own numbers (or size the file up front with
   grep/head/wc -l) instead of guessing again.
2. **git-add-cant-stage-untracked-deletes** — `git add <path>` cannot stage the deletion of a file
   git never tracked; use `rm` directly.
3. **git-pull-rebase-needs-clean-tree** — `git pull --rebase` requires a clean working tree; check
   for and stash/commit unstaged changes first.
4. **macos-timeout-is-bsd-not-gnu** — macOS's default `timeout` isn't GNU `timeout`; use `gtimeout`

5. **transient-auth-failure-retry-not-reconfigure** — a fresh, valid token flipping
   401↔200 mid-session is usually transient server-side instability; retry/`/login` rather than
   rebuilding config.

**None of these have been written to the vault yet.** All 5 are candidates for Joe's review at this
same gate (task 6.2); PROPOSALS.md also notes an honest limitation on Group E specifically — unlike
Group D's "recall after a failure" cue, these often fail on the *first* attempt, before any
failure-triggered recall would fire, so it's genuinely less certain a note gets recalled in time.

## 8. Limits

This section is required to be read in full before the gate decision. Every item below is a real,
sourced gap or caveat in the measurement — none are resolved here; they are flagged for the
critical joint review.

**a. The F1 anomaly — now a perfect 150/150, which sharpens rather than softens the concern.**
0/150 moments have `memory_existed==false`. The 3 originally-null checks were re-run for real in
the 2026-09-04 closeout (DERIVED mode, isolated scratch vault, phrases generated from chunk
context since all 3 transcripts were retention-deleted) — all 3 returned true, independently
reproduced byte-for-byte by an adversarial verifier. **But the recheck also demonstrated
concretely why 100% must be read narrowly:** `audit_moments.py` sets `memory_existed = True`
whenever the scratch `engram query` returns *any* non-empty result (`len(items) > 0`, no
similarity threshold) — each recheck returned ~45 items whose *top hit was topically unrelated to
the moment* (e.g. a property-based-testing note, score 0.607, for a go-test-timeout moment). F1
measures "the vault had something matching these phrases," not "a relevant memory existed."
**Corroborating evidence:** of the 150 matched memories, ~98% were judged `generic` rather than
`specific`, and 0 matched a `chunk`- or `qa`-kind memory despite those being valid categories
(`scorecard-main.json` `memory_kind_breakdown`). **A related "suspiciously clean" pattern in F3:**
among the 38 non-null `search_targeted_right_thing` verdicts, 0 are `false` — the judge never once
said a real search was mistargeted (a separate mechanism from F1's no-threshold check). Flagged
as-measured (`scorecard-main.json` F1 `extra.surprising_finding`). The Tier-1 measurement (§5c) confirmed this concretely — 90/96 no-search moments had nothing relevant in their top-5 despite F1's 100% existence rate, and 5 of 6 initially-'relevant' grades failed strict counterfactual arbitration.

**b. `note_superseded_correctly` — previously a complete field gap, now CLOSED.** The original run
left it null for all 150 moments. The 2026-09-04 closeout judged it for real over the 7
`note_written==true` moments: 3 supersessions correct, 1 incorrect, 3 not-applicable (no
supersession occurred) — **supersession correctness 3/4 = 75% among actual supersessions**, on a
very small n. The other 143 moments carry the mechanical reason `not_applicable_no_note_written`
(`scorecard-main.json` W3 `extra.supersession_correctness`).

**c. D1's checkable denominator is now n=4 of 28 (raw n=2 + 2 chunk-recovered)** — still the
single most important sample-size caveat in this report. The 2026-09-03/04 recovery (§5b) means
every genuine non-fork dispatch in the corpus (4 of 4) is now checked, but half the denominator is
chunk-derived (`judged_from='chunks'`, with candidate lists that are floors, not complete sets —
§4), and **n=4 remains far too small to generalize to all 28 dispatch moments**. Full breakdown in
§4; not re-derived here.

**d. Per-repo skew** — 2 of 7 repos account for 76.7% of moments, a deliberate consequence of D-A's
multi-repo sampling design. Full breakdown and rationale in §3; not re-derived here.

**e. The `failure_category` prompt-scope gap — CLOSED by the 2026-09-03/04 rescope (a post-hoc
fix Joe directed at this gate, not part of the original run).** The original run's judgment
prompt asked for `failure_category` only on `moment_type=="failure"` moments, leaving 22/50
failure/correction/rework moments (44%) and 45 success/dispatch lost lessons uncategorized — the
state an earlier draft of this section documented as an open gap. Per Joe's direction
(2026-09-03), the tool was fixed first — `audit_moments.py`'s judgment prompt now asks a

  §5b): 9 judged, 1 honestly nulled on the judge's own insufficient-context self-report

Post-merge state (`scorecard-main.json`, rebuilt): `failure_category` is populated for 94/150

**f. The fork-context judgment fix's residual findings** — see §5's two-part takeaway

**g. Point-in-time check reach.** From `corpus.json`'s `commit_frequency_by_month_last_12_months`:
the vault has 42 commits total, with commit counts of 9 (2026-06), 3 (2026-07), and 30 (2026-08 —
30 of those on a single day, 2026-08-29). The vault's own interpretation: moments dated
2026-06-02 through 2026-08-29 get an exact (DERIVED) point-in-time check; moments predating
2026-06-02 would fall back to the approximate (ESTIMATE) check. **The actual finding:** per
`scorecard-main.json`'s F1 `extra.derived_vs_estimate_among_existed_true`, **150/150 completed
existence checks used the exact DERIVED method — 0 fell back to ESTIMATE** (147 in the original
run + the 3 closeout rechecks). This means the vault's
git history covers this entire corpus's time range; the ESTIMATE fallback was never actually needed
in this run. **Upper-bound caveat (not previously disclosed):** DERIVED only has a documented lower
bound (git history reaching back far enough); it has no upper bound in the code — the checkout logic
takes "the last commit at or before the moment's timestamp," with no check for how far *after* the
vault's last commit that moment falls. **19/150 moments (12.7%) are timestamped after the vault's
last commit** (2026-08-29), up to 2026-09-01 — independently confirmed by direct query — and every
one of them still carries `derived`. Their point-in-time checkout can be up to ~3 days stale
relative to the actual moment. This doesn't make those checks wrong (nothing changed in the vault
during that window, since 2026-08-29 IS the last commit), but the DERIVED label alone doesn't
signal it — a reader would need to know this to judge freshness.

**h. Detector conservativeness — pre-registration AND a real post-hoc spot-check.** Full detail in
`SPOT_CHECK.md`; summary here.

- **Pre-registration:** `CALIBRATION.md` measured a **0/6 (0%) miss rate** pre-run on a 12-window,
  4-repo, hand-labeled calibration sample. Its own hedge: "n=6 is a small sample... a somewhat
  higher real-world miss rate on the full corpus is entirely plausible. Do not treat 0% as a tight
  statistical bound." It also explicitly promised a larger post-run check — "the true miss rate will
  be better estimated after task 5.1's larger hand-checked spot-sample" — **which an earlier draft
  of this report failed to disclose was never performed.**
- **That gap is now closed:** a real spot-check ran against actual production data (`full_run`/
  `refill` stages, not the original 12 windows), same blind-independent-then-compare method — 15
  windows across all 4 dispatch types and **6 of the corpus's 7 repos** (`targ` has zero
  `full_run`/`refill` moments — all 8 are `pilot`-stage, separately verified per task 4.3, not
  independently re-checked by *this* file).
- **Real result: 2 misses out of 22 independently-found real moments = 9.09% miss rate** — inside
  CALIBRATION.md §6's tightest proposed band ("≤10% missed... a pass with confidence to spare"),
  comfortably below the 15–20% upper tolerance and its ~25% "real problem" line.
  1. A successful `openspec-sync-specs` completion in a phone-llm transcript — only the dispatch was
     captured, not the successful outcome.
  2. A second, structurally-identical token-limit failure in a phone-llm fork transcript — the
     detector caught the first occurrence and the downstream rework/success, not this second
     discrete failure.

  Both are a *duplicate/downstream* moment next to one the detector did catch, not a blind spot on
  a novel failure mode.
- **A larger, more important secondary finding:** the gap between what the detector flagged and
  what the independent read confirmed is much bigger than 2 misses (53 detector-flagged candidates
  vs. 22 independently-confirmed real moments across the same 15 windows) — **and at least some of
  that gap looks like the independent reviewer under-counting, not the detector over-flagging**,
  which would push the true miss rate *higher* than 9.09% if so. `SPOT_CHECK.md` discloses this in
  full, including two windows where a direct re-read confirms the detector's flagged moments were
  probably real. This is a genuine open question this audit doesn't resolve, not a comfortable
  "false positives, filtered out for free" story.
