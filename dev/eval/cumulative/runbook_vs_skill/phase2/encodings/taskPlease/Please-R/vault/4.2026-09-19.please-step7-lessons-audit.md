# Please sub-runbook — Step 7 lessons audit and the LESSONS handoff

Before invoking the closing `/learn`, run the **lessons audit** over the cycle's mechanical corpus:

- every pre-registered STOP that fired
- every gate FAIL verdict
- every commit whose message contains CORRECTION, supersede/superseded, instrument-invalid, or redraw/redrawn
- every mid-cycle escalation to the user

Map each item to the vault note that captures its lesson, or write the one-line "no lesson: <why>". Unmapped items are reversal handoffs for the closing learn (its Step-2 kind 3). The audit list (item → note-or-no-lesson) appears in the cycle's closing report to the user. The audit is failure-shaped by design; positive reinforcement (confirmed approaches, self-validated bets) has no mechanical marker and is captured by the closing `/learn`'s Step-2 kind-4 scan, not here.

**WIKILINK SYNTAX IS REQUIRED WHEN YOU CITE A VAULT NOTE.** Every vault-note reference in the audit list — and in any structured field or report you write — MUST be written as `[[note-basename]]`: the note's full basename (for example its number, date, and slug) wrapped in DOUBLE SQUARE BRACKETS. Plain text ("note 186", "the doc-scrub note", a bare basename without brackets) is NOT a citation and is wrong. Re-read each citation before you send the report and fix any that lack the brackets.

For each lesson this cycle is about to capture, ask which artifact that already existed
should have surfaced it first. Before writing a new note, search the vault for one that
already covers the situation. If a note existed but did not surface at the moment it
was needed, check whether its `situation:` line matches how the moment actually
presented; if it doesn't, reword the note — that beats writing a second note on the
same lesson. A vault note is the user's own and takes effect on their next recall;
anything that ships from this repo instead — code, skills, guidance — makes the user
wait on a release, so propose that only as a last resort, and never file it
automatically.

**The LESSONS: handoff.** Every dispatched unit's completion report ends with a `LESSONS:` line (the route runbook's completion-report contract; every dispatch prompt you write says so). The moment each unit's result came back, step 4 recorded that line verbatim in a running list, including `LESSONS: none` entries. That list is separate from the audit above and is not judged in-flight. Now: put the audit list in the closing report to the user, then run the `learn` skill again, handing it the full running list of `LESSONS:` lines (including any `none` entries) alongside the lessons-audit map above — `/learn`'s Step 2 curates that list against its own quality bar; this step does not pre-filter it. The learn skill's Step 2.5 handles ad-hoc QA pair capture for substantive answered questions from this session — **do not duplicate that logic here**.
