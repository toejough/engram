red_flags:

    - 'refs/original/ or the reflog alone is not a durable recovery method: reflog entries expire (git''s default gc.reflogExpire is ~90 days, sooner if anyone runs git reflog expire or git gc manually), and git-filter-repo — unlike git filter-branch — never creates refs/original/ in the first place; only step 1''s bundle or SHA-file artifact, written before the rewrite, survives both'
    - step 6's GitHub support purge request is GitHub-specific — on a non-GitHub or unidentified remote there is no equivalent guarantee that unreachable objects are ever purged; rotate the actual leaked secret instead of relying on any host-side history purge
    - 'about to run a history rewrite scoped with -- --all (or any all-refs scope) while a backup branch or tag exists in the repo: -- --all rewrites every ref it can see, including that backup, so it provides no recovery path afterward — step 1''s artifact (bare SHA file or bundle), created outside the ref space before rewriting, is what actually survives'

    - 'about to use bare --force instead of --force-with-lease for the push: --force overwrites without checking whether the remote changed since your last fetch, silently clobbering a concurrent push from someone else'

1. Before rewriting, create a durable recovery artifact for the pre-rewrite tip that does not depend on the reflog or refs/original — e.g. `git bundle create <path>.bundle --all` (captures every ref and object; survives even if the local repo is later deleted) or record the bare SHA via `git rev-parse HEAD` in a plain-text file kept outside the repo. Do not rely on refs/original/ or the reflog alone: reflog entries expire (git's default gc.reflogExpire is ~90 days), and git-filter-repo — unlike git filter-branch — does not create refs/original/ in the first place. This artifact is additional insurance, not a replacement for steps 2-3's own local recoverability.
2. Scope the rewrite to explicit refs instead of rewriting every ref: for git filter-branch this means avoiding '-- --all'; for git-filter-repo this means passing --refs <ref> (e.g. --refs main) for the ref(s) actually being rewritten, instead of letting it process every ref by default — --refs also implies --partial, which is what keeps the reflog and local objects intact (see step 3). A backup branch (or tag) is not a safe exception either way, since an unscoped rewrite touches every ref it can see, backup refs included; step 1's artifact is what survives even that.
3. Run the history rewrite (e.g. git filter-branch ... -- --all, or git filter-repo --refs <ref> ...). Always avoid git-filter-repo's default post-rewrite gc: passing --refs per step 2 already does this (it implies --partial), or pass --no-gc explicitly if you cannot scope with --refs. Do this even though step 1 already created an external durable artifact — skipping it needlessly prunes the pre-rewrite commits (and expires the reflog) out of the local repo's own object store for no benefit; see the red flags below.
4. Before force-pushing, run git fetch to refresh local refs/remotes/origin/* — filter-branch also rewrites local tracking refs, so a stale tracking ref will fail the --force-with-lease check.
5. Force-push with --force-with-lease now that the lease compares against the freshly-fetched real remote state.
6. If the rewrite was meant to scrub truly sensitive data: on GitHub, unreachable objects are retained by SHA until server-side GC — file a GitHub support request for a full purge. On any other remote (GitLab, Bitbucket, a self-hosted server, or when you cannot identify the host), do not assume a GitHub-style purge request exists or applies — check that host's own support/admin channel for an equivalent, and treat the secret as exposed regardless: rotate or invalidate the actual leaked credential/key/token, since a history rewrite alone never guarantees removal from every clone, fork, or cache that already fetched it.
