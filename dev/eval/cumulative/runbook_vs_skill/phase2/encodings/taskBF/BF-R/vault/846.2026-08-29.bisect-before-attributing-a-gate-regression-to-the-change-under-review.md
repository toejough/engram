---
type: runbook
tier: L2
situation: a trap/eval gate (gate.py, crowded_gate.py, or similar) returns RED on the current HEAD of a branch/change under review, and the natural next step is to apply that change's own prescribed fix for the regression
done_when: the gate has been re-run against the commit immediately preceding the change under review, the verdict compared against the original RED result, the regression correctly attributed as pre-existing (with a separate follow-up issue filed, and its fix applied to this change only when step 6's narrow exception holds) or caused by the change under review, and the original HEAD/branch has been restored and rebuilt before reporting
red_flags:
    - A peer or teammate says "I've seen this exact pattern before, it's definitely X" -- their past experience describes their own code, not this change; pattern-matching on the symptom (e.g. a bare error at a given line) is not pattern-matching on the cause, since a pre-existing bug looks identical to a newly-introduced one. Verify against the pre-change commit yourself (steps 1-5) rather than trusting the pattern match.
    - A deadline is approaching right after the gate fails, making it tempting to skip the bisection and apply the suggested fix directly -- the checkout/rebuild/re-run check (steps 1-4) takes about two minutes; applying a wrong fix means a second gate failure and another merge attempt, which costs more time than the deadline it was meant to save.
    - Feeling confident the change under review caused the failure because you wrote it (or because the change "looks obviously related") -- confidence is not causation; a change-unrelated file can still trigger a gate failure if the pre-change commit was already broken. The gate verdict on the pre-change commit (steps 2-5) is the only evidence, not your familiarity with the diff.
    - An authority figure (senior engineer, reviewer) has already reviewed the code and says it's the cause, so it feels safe to skip the bisection check -- code review evaluates what the PR contains, not whether the pre-change commit is actually green; the reviewer is not claiming to have tested main. Verify it yourself (steps 1-5) rather than treating a code review sign-off as a substitute for bisection.
    - The task/request explicitly says to make this gate/check pass, but this runbook's own default step 6 wording says not to apply the fix -- reading the general default as if it overrides an explicit instruction for THIS task is backwards; check step 6's narrow exception (explicit instruction + small, clearly-scoped fix) before stopping to ask permission the instruction already granted.

1. Identify the commit immediately preceding the change under review's relevant commits.
2. Check out that preceding commit.
3. Rebuild the artifact under test from that commit.
4. Re-run the identical gate (e.g. gate.py --tier smoke) against that rebuilt artifact.
5. Compare this verdict to the original RED verdict observed on the change under review's HEAD.
6. If the same failure reproduces on the pre-change commit: the change under review is NOT the cause. File the pre-existing regression as its own separate issue for dedicated investigation. Default: do not apply its prescribed fix as part of this change -- an unrelated fix folded into this change is scope creep, even when it's tempting. Narrow exception: apply the fix as part of this change ONLY when both hold -- (a) the current task/request has EXPLICITLY instructed making this specific gate/check pass (e.g. "fix what's needed so the gate passes"), not merely "a gate failed, handle it" in the abstract; and (b) the pre-existing issue's fix is small and clearly scoped (e.g. a stray debug statement, an obviously-wrong constant), not a design change needing its own review. When the exception applies, still file the follow-up issue, noting the fix was pre-existing and out of the current change's original scope -- do not stop to ask permission for it, since the explicit instruction already grants it. Outside the exception -- when the instruction is only the general "a gate is failing, look into it" -- attribute and stop there; do not casually fix, and do not ask to apply a fix nothing has authorized.
7. If the failure does NOT reproduce on the pre-change commit: the change under review is confirmed as the cause -- its prescribed fix (if any) applies.
8. Restore the original HEAD/branch and rebuild the artifact before reporting results.
