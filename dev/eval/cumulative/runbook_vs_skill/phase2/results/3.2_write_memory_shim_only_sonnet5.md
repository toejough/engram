## How "runbook fetched" was determined — transcript evidence

The harness's own `found`/`found_via` field (engram-query-surfacing based) is **not** the right signal
for this task (design D4's primary gate is a *named* `engram show <basename>` fetch, since write-memory
has no trigger and is never discovered by a generic query) — it is included above only as a secondary
cross-check. I read each trial's transcript directly for any `engram show` Bash call, and for how the
`[[6a.2026-09-22.write-memory-compose-execute-verify]]` wikilink instruction was actually acted on:

- **Trial 0**: zero `engram show` calls anywhere in the transcript. The `learn` skill's own text (verified
  correctly converted: `**REQUIRED NEXT ACTION:** fetch and follow [[6a.2026-09-22.write-memory-compose-execute-verify]]`)
  was acted on by calling the **Skill** tool with `skill: "write-memory"` — twice, once per write. Both
  results: `<tool_use_error>Unknown skill: write-memory</tool_use_error>` (no such skill exists in arm R,
  correctly). After each error, the agent composed the `engram learn` command itself via trial-and-error
  (`engram learn feedback --help`, `engram learn fact --help`, `engram learn feedback --common-learn-args --help`,
  several scratch probe commands against a throwaway `test-slug` note it then deleted) — never reading the
  runbook. It also briefly guessed `--tags "component/cooling"` in one scratch probe, got
  `Error: flag provided but not defined: --tags`, and self-corrected to `--tag` for the real writes —
  the exact "guessed wrong, errored, retried, ended up correct despite never reading the runbook" failure
  mode design.md's Risk section named as the reason the fetch check must be the primary gate, not the
  tag-flag divergence.
- **Trial 1**: zero `engram show` calls. One `Skill{skill: "write-memory"}` attempt (for the first write
  only), same `Unknown skill: write-memory` error, same self-composition fallback for both writes. Also
  guessed `--tags "component/test"` once in a scratch probe (`Error: flag provided but not defined: --tags`),
  then used `--tag` (quoted) in both real writes.
- **Trial 2**: zero `engram show` calls, and **no** `Skill{write-memory}` attempt at all — after
  `Skill{learn}`, the agent went straight to composing `engram learn fact` twice, using `--tag` (never
  `--tags`) from the first attempt on both writes. The one candidate evidence for "read via query": the
  initial `engram query` call (recall's own Step-2 sweep, run before any write) returned the write-memory
  runbook's **full content** as its lowest-ranked item (score 0.298, rank 7 of 7, `kind: runbook`) inside a
  20KB result blob about printer-warping causes. Nothing in the transcript — no quote, no reference to the
  compose-block syntax, no mention of the runbook — shows the agent attended to that specific item rather
  than the six on-topic items it was actually searching for. I'm treating this as a weak, unconfirmed
  signal, not a pass: the harness's own `found_via=engram_query` flag (which only checks basename
  *presence* in a pre-mutation query result, not attention/use) is true for this trial, which is why it's
  the one trial with `found=True` in the raw jsonl — but "included in a bulk result" is not "fetched and
  followed" per design D4's literal wording.

**Root-cause read**: the call-site wording itself is correct (verified against the live fixture files —
this is not a re-run of task 2.4's already-passed review). The failure is behavioral: the model reads
"fetch and follow `[[wikilink]]`" and, having just used the `Skill` tool twice for `recall`/`learn` in the
same session, defaults to trying `Skill{name}` again rather than recognizing the wikilink as an
`engram show` cue — then, on the inevitable "unknown skill" error, falls back to composing from
priors/`--help` rather than recovering via `engram show`. This is the same class of finding vault note
1039 already flagged for query-triggered runbooks (a hand-verified retrieval check doesn't predict real
agent behavior) — here for a *named* (non-query) fetch instead.

## A scoring-harness artifact found in `steps.json` (not applied — flagging only, per task scope)

Steps 4 and 8 require `--tag\s+component/(electrical)?` with **no** tolerance for a quoted value. Trial 1's
writes used `--tag "component/cooling"` / `--tag "component/electrical"` (quoted, fully correct, and
verified present in the actual written vault notes) — the quote character breaks the regex, producing a
false-negative on both steps. Verified directly: `--tag component/cooling` matches the step-4 pattern,
`--tag "component/cooling"` does not. This mirrors the semicolon-exclusion bug task 1.4's report already
found and fixed in this same file. If corrected, trial 1's `followed_all` would be 10/10 (not 8/10) and the
raw table's `followed_all` row would read 2/3, not 1/3 — **this does not change the D8 verdict**: the
decisive blocker is the validity gate (0/3, including 0/2 on the corrected passing set), not composition
scoring. I did not touch `steps.json` — fixing it is out of this task's scope (3.1–3.3: run, record, judge
the bar) and would not change the outcome either way.

Trial 0's tag miss (bare `--tag electrical`, missing the `component/` family) is a **real** composition
defect, not a scoring artifact — confirmed against the written vault note's `tags:` list.
