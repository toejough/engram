# 792g21 parent-sync - Adoption Audit

Audit of [792a21 parent-sync](../792a_product-spec.md#792a21-added-parent-sync) (37 requirements, 178 scenarios) and the 45 [792b](../792b_technical-spec.md) requirements whose `Supports:` lines cite its scenarios, against a binary built from `dda22904`.

Method:

- **Real exchange.** A parent `engram serve` on a loopback port and a child with `ENGRAM_PARENT` set to it, each with its own temp vault, `HOME` and `XDG_DATA_HOME`. Nothing touched a real vault or config, and `ENGRAM_PARENT` was never set globally.
- **Fake parent.** A small Python server on loopback answered with a loop 409, a plain 409, a 500, a malformed receipt and a parent with no `vault_id`.
- **Test suite.** `targ test` passes. `targ check-full` passes except `check-uncommitted`, which fails only because this audit was not yet committed.
- **Not run.** `engram update` clones the repository from the network, so the update notice, `--backfill-identity`, `--reparent-luhmann` and skill registration are covered by their tests and code only. User detection cannot be emptied on this host, and a model-ID mismatch cannot be produced with the one bundled model.

Result:

- Parent-sync requirements: 1 covered by #795, 5 doc fixed, 29 match, 1 code bug (#836 for 792a21zg), 0 unclear.
- Parent-sync scenarios: 1 covered by #795, 2 doc fixed, 175 match, 1 code bug (792a21zg1g, #836; added for the ruling).
- Technical requirements: 1 doc fixed, 42 match, 2 code bug (#829 for 792b36c4, #836 for 792b37c15), 0 unclear.
- Code bugs after Joe's rulings (2026-10-10): [#829](https://github.com/toejough/engram/issues/829) (a self-parent vault still queues offers; 792b36c4) and [#836](https://github.com/toejough/engram/issues/836) (the use signal is sent after a failed local write; 792a21zg and 792b37c15). Existing issues #782 (`scanDedupeNotes` reads each note twice), #785 (no parent-version check) and #786 (self-parent guard on a transient vault-ID read failure) describe real gaps that the spec does not promise away; they are referenced in the rows they touch. #795 covers the vault-creation exception to [792a21m A vault with no parent behaves as it always did](../792a_product-spec.md#792a21m-a-vault-with-no-parent-behaves-as-it-always-did).

Doc fixes (the code reflects a later, deliberate decision; IDs unchanged):

- [792a21n A local write is offered to the parent](../792a_product-spec.md#792a21n-a-local-write-is-offered-to-the-parent): ~~`--pending=false` clears the marker like `--clear-pending`~~ Reverted by the orchestrator: the classifier treats a false `Pending` argument like `--clear-pending`, but the CLI cannot pass it; `engram amend --pending=false` fails with `unsupported value type: *bool` (#797). The spec names only `--clear-pending`.
- [792a21s An unreachable parent is backed off](../792a_product-spec.md#792a21s-an-unreachable-parent-is-backed-off): a 5xx, and a 2xx offer answer that cannot be decoded, back the parent off.
- [792a21v A reply that is not a valid receipt is not recorded](../792a_product-spec.md#792a21v-a-reply-that-is-not-a-valid-receipt-is-not-recorded) and its scenario [792a21v1b A malformed receipt is not recorded](../792a_product-spec.md#792a21v1-uat-scenarios) (copied in [792b5d Product-Scenario Mapping](../792b_technical-spec.md#792b5d-product-scenario-mapping)): a malformed receipt also backs the parent off.
- [792a21y A looping offer is refused](../792a_product-spec.md#792a21y-a-looping-offer-is-refused), its scenario [792a21y1a A cycle rejects the entry and continues](../792a_product-spec.md#792a21y1-uat-scenarios) (copied in [792b36d Product-Scenario Mapping](../792b_technical-spec.md#792b36d-product-scenario-mapping)) and [792b36c12 A looping offer](../792b_technical-spec.md#792b36c12-a-looping-offer) with its scenario: the refusal is an answer and resets the failure count, so 'counters left alone' was wrong. The stale comment above `Test792b36c12a1_DrainOutbox_CycleRefusalRejectsAndContinues` in `internal/cli/outbox_test.go` now says the same.
- [792a21zd A pulled-down note is an exact-content local pending offer](../792a_product-spec.md#792a21zd-a-pulled-down-note-is-an-exact-content-local-pending-offer): `vocab_version` is also stripped.

Code bug [#836](https://github.com/toejough/engram/issues/836): [792a21zg A pull-down tells the parent the note was used](../792a_product-spec.md#792a21zg-a-pull-down-tells-the-parent-the-note-was-used) and [792b37c15 Telling the parent the note was used](../792b_technical-spec.md#792b37c15-telling-the-parent-the-note-was-used) say the signal follows a pull-down or a skip, but the code sends it after a failed write too. It was `unclear` (a harmless best-effort hint); Joe ruled it a bug and the spec now says a failed local write sends no signal.

Also noted, not changed: `stampNoteXID` (`internal/cli/outbox.go:975`) is unused outside its test export.
