# 792g10 vault-migration - Adoption Audit

Audit of [792a10 vault-migration](../792a_product-spec.md#792a10-added-vault-migration) and the [792b27 note-reparenting](../792b_technical-spec.md#792b27-added-note-reparenting) requirements, plus the 792b11 and 792b28 requirements whose `Supports:` lines cite its scenarios. Method: read the code, then ran a binary built from this tree (`go build -o ... ./cmd/engram`) against temp vaults with `HOME`, `XDG_*`, `TMPDIR` and `ENGRAM_VAULT_PATH` pointed at temp dirs. `engram update` was driven with `ENGRAM_UPDATE_REEXEC=1` from a checkout (so it skips the clone and install), and the flat-vault notice, `--reparent-luhmann` (derive, dry run, apply) and `--backfill-identity` (notice, dry run, apply, repeat, anchors, CRLF) were all exercised.

Summary: two code problems were found and filed as [#813](https://github.com/toejough/engram/issues/813) (a `sibling` answer can never be applied) and [#814](https://github.com/toejough/engram/issues/814) (answers are not validated against the derived candidates). One scenario wording was fixed in the docs ([792a10d1d An unknown note](../792a_product-spec.md#792a10d1-uat-scenarios), also copied in 792b). Everything else matches. Not run: a full `engram update` with the clone, install and hand-off; a failing ingest or prune stage on the binary; the empty user-detection cases (the OS username always resolves); the `register-skills --adopt` caller of the rename primitives. Nothing here is covered by #795/#796.
