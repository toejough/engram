# How Systems Compose Multiple Simultaneously-Applicable Procedures
## A briefing for building composition into a note-retrieval procedural memory (engram-style)

**Framing.** The engineer's problem: an agent retrieves N procedural notes — "TDD discipline," "Go coding standards," "remote-env dev steps" — that all apply *right now*, and must act coherently. Fifty years of cognitive architecture, planning, and robotics work has faced exactly this problem, and the solutions cluster around one recurring architectural insight, stated up front because everything below instantiates it:

> **Separate constraint composition (parallel, safe to blend) from action selection (serial, needs arbitration).** Every mature architecture lets many knowledge sources *elaborate* the situation simultaneously, but forces the *next action* through a serial choice point with an explicit tie-breaking scheme. Incoherent blends happen when systems skip the choice point and average at the action level.

A second cross-cutting distinction that organizes the whole space — worth adopting as vocabulary:

- **Constraint-like procedures** (Go standards, lint rules, "wrap errors with %w") compose by **conjunction**. They constrain different aspects of the same actions. Like non-colliding CSS properties, they blend safely.
- **Plan-like procedures** (remote-env setup steps, release steps) compose by **sequencing/interleaving**. They need ordering decisions, not blending.
- **Same-slot procedures** (two different "commit" procedures) compose by **arbitration or supersession**. Exactly one must win; blending is the failure mode.

TDD + Go standards + remote-env is mostly case 1 + case 2 — which is why in-context blending usually works for it. The dangerous case is 3, and it is rarer but silent.

## 1. Production systems: ACT-R and SOAR

### ACT-R — utility-based conflict resolution, serial firing

In ACT-R (Anderson), procedural knowledge is a set of production rules (condition → action over buffer contents). Each ~50 ms cycle, *all* productions whose conditions match the current buffer state form the **conflict set**, and **exactly one fires**. Selection is by expected **utility**: classically `U = P·G − C` (probability of achieving the goal × goal value − cost), in modern ACT-R a learned utility per production updated by a temporal-difference-like rule from rewards, with selection noise (effectively a softmax over utilities). Key properties:

- **The serial bottleneck is the coherence mechanism.** ACT-R never blends two productions' actions. Composition of multiple "procedures" is achieved *over time*: rules from different skill-sets interleave cycle by cycle, threaded through shared goal/problem state. Salvucci & Taatgen's **threaded cognition** extends this to multitasking: multiple goal threads coexist, their productions interleave on the single serial procedural resource, and interference is predicted precisely where threads contend for a shared resource (a good formal model of *why* interleaving two procedures is costly).
- **Production compilation** (proceduralization): when a production retrieves a declarative instruction and another production acts on it, the pair gets compiled into one new specialized production. This is the architecture's model of how *written instructions become skills* — directly analogous to an LLM agent turning "notes it must re-read" into consolidated procedures. Taatgen's instruction-following models show early behavior is slow and retrieval-bound, later behavior is compiled and instruction-free.
- Conflict among same-slot rules is resolved by utility (experience-weighted), not by declared priority — ACT-R learns which rule wins from outcomes.

### SOAR — parallel elaboration, preference-based decision, impasses, chunking

SOAR (Laird, Newell, Rosenbloom) makes the elaborate/select split explicit and is the single most instructive architecture for this problem:

- **All matching productions fire in parallel** — but productions cannot take actions. They only (a) elaborate the state with inferences and (b) propose/evaluate **operators** by emitting **preferences**: acceptable, reject, better/worse-than, best, worst, indifferent. This is a *richer* arbitration language than scalar priority — it supports context-dependent partial orders ("in a Go repo, prefer the targ-based check operator over raw go test").
- A fixed **decision procedure** combines preferences and selects exactly one operator per cycle. Parallel knowledge, serial action.
- When preferences are insufficient — a **tie**, a **conflict** (A better than B *and* B better than A), or no-change — SOAR does not guess. It declares an **impasse** and automatically creates a **subgoal** whose task is to resolve it (e.g., look-ahead evaluation of the tied operators, or retrieval of more knowledge). Deliberation is the fallback for failed arbitration, not the default.
- When the subgoal resolves the impasse, **chunking** compiles the resolution path into a new production, so the same impasse never recurs — the system converts one-time deliberation into permanent procedural knowledge.

**How production systems avoid incoherent blends:** (1) actions pass through a single-choice decision cycle; (2) arbitration is explicit (utility or symbolic preferences); (3) failed arbitration escalates to deliberation rather than averaging; (4) resolutions are cached as new rules. All four map cleanly onto LLM-agent design (see §6, §8).

## 2. HTN planning — methods, backtracking, interleaving, critics

Hierarchical Task Network planners (NOAH — Sacerdoti 1975; NONLIN — Tate; SIPE — Wilkins; O-Plan — Currie & Tate; SHOP/SHOP2 — Nau et al.) decompose compound tasks via **methods**: `task → partially-ordered network of subtasks`, guarded by preconditions.

- **Multiple applicable methods** are handled by *search*, not blending: the planner commits to one method, and **backtracks** if it dead-ends. SHOP2 tries methods in a declared order (a priority field, effectively) with depth-first backtracking. No HTN planner merges two methods for the same task — methods are same-slot procedures and the architecture treats them as alternatives, period.
- **Interleaving**: because subtask networks are *partially* ordered, subtasks originating from different parent tasks can interleave in the final plan. SHOP2 explicitly supports interleaved decomposition trees — necessary when two high-level tasks share a resource or one's step must slot inside the other's (your "remote-env steps wrap around the TDD loop" case is precisely an interleaved decomposition).
- **Critics** (NOAH, elaborated in NONLIN/O-Plan) are the deepest precedent for note composition. NOAH expanded each subtask *independently* (optimistically assuming no interaction), then ran critics over the joint plan:
  - **Resolve-Conflicts** — detect when one branch clobbers a precondition another branch needs; repair by ordering (promotion/demotion).
  - **Eliminate-Redundant-Preconditions / Use-Existing-Objects** — detect that two branches contain the *same* step and **merge the duplicates**.
  - O-Plan generalized this into an agenda of flaws/issues plus constraint managers (TOME/GOST — tables of effects and goal structure) that continuously detect cross-branch interactions.

  **The compose-then-critique pattern — expand each procedure independently, then run a dedicated interaction-detection pass over the combined plan — is the proven answer to "how do I merge N procedures that mostly don't interact but occasionally clobber or duplicate each other."** It is cheap in the common case (no interactions → no work) and targeted in the rare case.

## 3. Behavior-based robotics and behavior trees

- **Subsumption** (Brooks 1986): concurrent behavior layers; higher layers **suppress** lower layers' inputs or **inhibit** their outputs. Arbitration is fixed-priority, wired-in, winner-takes-the-actuator. Lesson: dirt-cheap static priority works when the priority order is genuinely context-independent.
- **The blending cautionary tale — motor schemas** (Arkin): the one major family that *did* blend (vector-summing concurrent behaviors' outputs) is famous for its pathologies: canceling vectors, local minima, oscillation between obstacles. This is the robotics literature's empirical verdict on averaging same-slot outputs — the direct analog of letting an LLM "split the difference" between two commit procedures. DAMN (Rosenblatt) softened winner-take-all into *voting over concrete candidate actions* — arbitration over actions, not blending of commands — and worked much better.
- **Behavior trees** (game AI via Halo 2 / Isla 2005; formalized for robotics by Ögren, Colledanchise): **sequence** nodes (do children in order, fail fast), **fallback/selector** nodes (try children in priority order until one succeeds — priority is literally child order), **parallel** nodes (explicitly marked as the only concurrent construct), re-evaluated reactively every tick. BTs are the modern consensus arbitration formalism precisely because they make priority, sequencing, and (rare, explicit) parallelism *first-class and inspectable*, and because subtrees are modular — a stored "commit" subtree can be grafted under any parent. BTs generalize subsumption (a fallback node over layers is dynamic subsumption).

## 4. Human skill composition (brief)

Four robust findings, each with a design moral:

1. **Hierarchical chunking** (Miller; Rosenbloom & Newell's chunking theory; motor-chunk studies, e.g. Verwey): routines are stored as nested chunks; experts execute at the chunk level. Moral: consolidate frequently co-retrieved procedures into one bigger procedure rather than re-composing every time.
2. **Task-set switching costs** (Rogers & Monsell 1995; Allport's task-set inertia): switching between two active procedures costs time and errors even with full warning; humans *serialize* rather than blend, and pay at the seams. Moral: interleaving is a real cost even for the best-known general intelligence; minimize forced switches per step.
3. **The central bottleneck / PRP** (Pashler): response *selection* is serial even when perception and motor execution parallelize — biology independently converged on ACT-R/SOAR's serial choice point.
4. **Capture errors** (Norman, Reason): when two routines share a prefix, the *stronger habit captures execution* at the branch point (driving toward the store, ending up at work). This is what arbitration-by-strength-alone does with same-slot procedures — the frequent procedure silently wins over the situationally-correct one. Moral for note stores: recency/frequency weighting alone will misfire exactly at shared-prefix branch points; specificity of context match must dominate strength.

## 5. LLM-era procedure composition

**How agents actually combine instruction sources today.** Claude Code-style stacks concatenate: system prompt + global CLAUDE.md + project CLAUDE.md + rules files + on-demand skills + retrieved memory notes. Precedence is *stated as prose convention* ("these instructions OVERRIDE defaults", "project overrides global") and *enforced only by model attention* — there is no arbitration machinery. This is in-context blending with textual precedence hints.

**Published work on instruction conflict:**

- **The Instruction Hierarchy** (Wallace et al., OpenAI 2024): trains models to prioritize system > developer > user > third-party content when instructions conflict; showed large robustness gains via synthetic conflict data. This is *trained-in tiered precedence* — the LLM analog of subsumption layers — and it partially works, which is evidence that declared tiers are a mechanism frontier models can respect. ([OpenAI](https://openai.com/index/the-instruction-hierarchy/), [Simon Willison's summary](https://simonwillison.net/2024/Apr/23/the-instruction-hierarchy/))
- **Constitutional layering** (Anthropic): principles composed as a ranked/sampled set applied at training time — composition resolved *before* inference, not at task time. Task-time analog: bake stable cross-cutting standards into always-loaded tiers, don't retrieve them.
- **Conflict-handling is measurably poor and, crucially, *silent***: ConInstruct (conflict detection/resolution benchmark) finds LLMs can often *detect* conflicting instructions but **rarely acknowledge them unprompted — they silently pick one side** ([ConInstruct](https://arxiv.org/pdf/2511.14342)). Related benchmarks — [A Closer Look at System Prompt Robustness](https://arxiv.org/pdf/2502.12197), [PRIME](https://arxiv.org/html/2606.22470), [IH-Benchmark](https://arxiv.org/abs/2607.25987v2), [Who is In Charge?](https://arxiv.org/html/2510.01228) — converge: hierarchy compliance is partial, and socially-salient or recent instructions often beat declared priority.
- **Context clash / confusion** (Breunig's failure taxonomy): *context clash* = accumulated contradictory context degrades reasoning; *context confusion* = superfluous retrieved content gets used because it's there — e.g., a quantized Llama 3.1-8B failing with 46 tools in context but succeeding with 19 ([How Long Contexts Fail](https://www.dbreunig.com/2025/06/22/how-contexts-fail-and-how-to-fix-them.html)). Anthropic's tool heuristic transfers verbatim to procedures: *if a human can't tell which of two retrieved procedures governs this step, the model can't either.* Also relevant: "LLMs Get Lost in Multi-Turn Conversation" (Microsoft/Salesforce 2025) — instructions revealed/revised across turns degrade performance sharply, i.e., accumulated near-conflicting procedure text is itself a tax.
- **Voyager** (Wang et al. 2023): the clearest published *explicit* composition — skills are executable programs indexed by description embeddings; top-5 retrieved; **new skills compose old ones by calling them as functions**. Composition lives in code space (a call graph), not in prose blending; the interpreter, not the LLM, guarantees coherent sequencing. ([Voyager](https://arxiv.org/abs/2305.16291))
- **Agent Workflow Memory** (Wang et al. 2024): induces reusable workflow templates from successful trajectories, retrieves relevant ones, and *injects them as in-context guidance* — retrieval-then-dump, composition left to the model. Notably AWM builds later workflows out of earlier ones at *induction* time (composition at write time, not read time). ([AWM](https://arxiv.org/abs/2409.07429))
- **Memp** (2025) adds a build/retrieve/**update** loop (add/modify/delete procedures on execution feedback — utility learning for notes) ([Memp](https://arxiv.org/pdf/2508.06433)). **LEGOMem** (Microsoft, 2025) decomposes trajectories into modular memory units and *allocates* them across orchestrator vs. task agents — finding orchestrator memory drives decomposition quality while fine-grained agent memory drives execution accuracy — i.e., *placement* is an arbitration decision, but in-slot use is still in-context ([LEGOMem](https://arxiv.org/abs/2510.04851)). **SayCan** (Ahn et al. 2022) deserves mention as a true published arbitration primitive: LLM likelihood × learned affordance value selects *one* skill per step — utility-based serial selection, ACT-R-style.

**Answer to the direct question — is there ANY published system that retrieves N procedures and composes them explicitly rather than context-dumping?** Essentially only in code space: Voyager (and descendants like Odyssey, and code-prompting work like ProgPrompt) compose retrieved skills via function calls; SayCan arbitrates serially via scores. For *prose* procedural memory — the engram case — no prominent published system performs explicit merge/arbitration over retrieved notes at read time; AWM, Memp, LEGOMem, and the 2025–26 procedural-memory wave all retrieve-and-inject and let the model blend. (Some very recent work — hierarchical procedural memory, compositional-retrieval benchmarks ([arxiv 2511.21730](https://arxiv.org/pdf/2511.21730), [2512.18950](https://arxiv.org/pdf/2512.18950)) — names compositional retrieval as an open problem, which corroborates that it is not solved practice.) **Explicit composition of prose procedures at task time is a genuine gap, not an overlooked standard technique.**

## 6. Does a strong LLM need explicit composition machinery?

The honest reading of the evidence:

**In-context blending suffices when** — (a) procedures are *different-concern* (constraint-conjunction: TDD + Go style + remote-env constrain different aspects; nothing to arbitrate); (b) conflicts are rare; (c) total procedure volume is modest (below confusion thresholds); (d) precedence, where needed, is stated in text (instruction-hierarchy training gives this real, partial force). This is why Claude Code's concatenation stack works as well as it does, and why AWM/Memp get gains with zero arbitration machinery.

**Blending demonstrably fails when** — (a) **same-slot conflict exists: the model resolves it *silently*** (ConInstruct) — you don't get an incoherent blend so much as an unflagged coin-flip, which is worse because it's invisible; (b) **volume grows**: context confusion causes use of irrelevant procedures and compliance decay as simultaneous constraints accumulate; (c) **position/recency effects** decide winners arbitrarily (lost-in-the-middle; last-instruction bias); (d) near-duplicate stale procedures coexist with current ones (context clash — the multi-turn "lost" result is this in slow motion).

**Conclusion for the engram case:** full production-system machinery (numeric utilities, formal preference calculus) is *not* warranted — LLMs don't reliably respect numeric priorities, and the common case (different-concern conjunction) needs nothing. What the failure evidence *does* motivate is machinery at three cheap points: **(1) write/curation time** — supersession and dedup so same-slot conflicts never reach the context (the vault-side fix for context clash); **(2) retrieval time** — scope-specificity ordering and a cap (the fix for confusion/volume); **(3) a conflict-surfacing rule** — because the model's silent-resolution default is the one behavior you must override in text (SOAR's impasse, as a prompt: "if two retrieved procedures prescribe incompatible actions for the same step, say so and adjudicate explicitly — never silently pick"). Note that resolving conflicts at write time is also how human memory does it (consolidation/interference-resolution), and it's what engram's `curate` covered/near/absent judgment already approximates.

## 7. Interleaving vs. sequencing: the arbitration-primitive catalog

When two procedures claim the same step ("two commit procedures"), the primitives on record:

| Primitive | Provenance | Mechanism | LLM-note transferability |
|---|---|---|---|
| **Specificity ordering** | OPS5 conflict resolution; CSS specificity | More-specific condition/selector wins | **High** — scope metadata on notes ("this repo" > "Go projects" > "all repos"); models follow "more specific instruction wins" well |
| **Recency** | OPS5 LEX strategy; ACT-R activation | Newest matching data wins | Medium — good tiebreak, bad primary rule (capture errors §4: strength/recency misfires at branch points) |
| **Priority fields / tiers** | Subsumption layers; BT fallback order; O-Plan agenda; OpenAI instruction hierarchy | Static declared rank | **High for few coarse tiers** (system>project>global is trained-in); low for fine numeric ranks |
| **Learned utility** | ACT-R; SayCan; Memp update | Outcome-weighted selection | Medium — engram's confidence decay is this; use to *prune at retrieval*, not to ask the model to weigh numbers |
| **Preference semantics** | SOAR (better/worse/best/reject) | Context-conditional partial order | Low as calculus; **high as prose**: "in X, prefer A over B" statements in notes are exactly SOAR preferences |
| **Explicit supersession** | TMS; nonmonotonic defaults-with-exceptions; SOAR reject | "A replaces B" edge; loser never surfaces | **Highest** — resolvable at curation time, zero read-time cost |
| **Impasse → deliberate → cache** | SOAR subgoaling + chunking | Escalate failed arbitration to reasoning; compile the ruling | **High** — surface conflict, adjudicate (or ask user), then `/learn` the merged ruling as a new note |
| **Compose-then-critique** | NOAH critics; O-Plan constraint managers | Expand independently; detect clobbering/duplicates; merge/order | High — a post-draft review pass over the combined plan |
| **Serial choice point** | ACT-R/SOAR decision cycle; PRP; DAMN voting | Exactly one procedure owns each step; interleave at step granularity (SHOP2 partial orders) | High — prompt discipline: "each step is governed by one procedure; name it" |

**Interleaving specifically:** the proven pattern is *partial-order interleaving with protection* (NONLIN/SHOP2): procedures contribute steps into one plan; ordering constraints are added only where a critic detects interaction. Threaded cognition and switch-cost data add: minimize the number of interleave points — chunk runs of same-procedure steps rather than fine-grained alternation.

## 8. Ranked shortlist for a note-retrieval agent memory

Ranked by (proven pedigree × cheapness × expected payoff for the engram-style case):

1. **Supersession at curation time** — *(proven: TMS, human consolidation, NOAH duplicate-merging; cheap: an `amends/supersedes` edge + retrieval honoring it)*. Same-slot conflicts ("two commit procedures") are resolved once, at write time, and the loser stops surfacing. Kills the silent-conflict failure mode at its source; zero read-time cost. Engram's amend/curate is already 80% of this — the missing 20% is retrieval *suppressing* superseded notes.
2. **Scope-specificity ordering + coarse tiers** — *(proven: CSS/OPS5 specificity; instruction-hierarchy training shows models honor few coarse tiers)*. Stamp each note with its scope; one standing rule: "more specific scope wins; ties → newer." Cheap metadata, and the only primitive with direct evidence that frontier models were *trained* to respect its shape. Avoid fine-grained numeric priorities — no evidence models respect them (speculative).
3. **Conflict-surfacing rule (SOAR impasse in prose)** — *(grounded in ConInstruct: detection exists, unprompted surfacing doesn't)*. One guidance line: on incompatible prescriptions for the same step, flag and adjudicate explicitly; never silently pick. Near-zero cost. *Speculative in degree* — compliance under context pressure is unmeasured; this is the cheapest thing worth eval-ing (a same-slot trap pair, RED = silent pick).
4. **Chunk the resolution (SOAR chunking / ACT-R compilation / AWM induction)** — after any adjudicated conflict or any repeatedly co-retrieved bundle, write the *merged* procedure as one new note superseding the parts. Proven in three independent literatures (and it's just `/learn` + supersession); also matches human chunking (§4). Turns read-time composition cost into a one-time write.
5. **Compose-then-critique pass (NOAH critics)** — when N plan-like notes feed one task, draft the combined plan, then one targeted check: clobbered preconditions, duplicated steps, ordering conflicts. Proven in planning; for an LLM it's a review gate (engram's `please` gates are the chassis). Moderate cost — reserve for multi-procedure plans, not every task.
6. **Retrieval cap + relevance pruning against context confusion** — *(grounded in the tool-count evidence and constraint-decay)*. Fewer, more-relevant procedures beat comprehensive dumps; engram's payload findings point the same way. Cheap; mostly already believed.
7. **Outcome-weighted note utility (ACT-R utility / Memp update)** — decay or boost notes on observed task outcomes, applied as retrieval-side pruning. Proven mechanism in ACT-R; *speculative plumbing* for note stores (attribution of outcome to note is the hard part; engram's confidence decay is a crude proxy).
8. **Code-space composition (Voyager)** — promote stable, frequently-composed procedures from prose notes to callable skills that invoke other skills; the runtime, not attention, guarantees sequencing. Proven in Voyager; highest adoption cost, and only pays for the stable head of the distribution — not a substitute for 1–5 on the long tail of prose notes.

**What remains genuinely speculative for LLM agents:** numeric utility arbitration in-context; formal preference calculi; reliable fine-grained interleaving under context pressure; and any read-time *automatic* merge of prose procedures (nobody has published one that works — see §5). The proven end of the list is heavily weighted toward **write-time and retrieval-time** mechanisms, which is convenient: those are exactly the points a zettelkasten memory system controls.
