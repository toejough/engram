## Why

Issue [#720](https://github.com/toejough/engram/issues/720): remote environments (app VMs with no local checkout, no binary path) currently cannot use the vault at all. A filesystem mount was considered and rejected — `flock` is advisory and does not reliably propagate across a host/guest virtualization boundary, and a mount cannot attribute a write to who actually made it. A client/server split solves both: the vault stays on one host, remote environments talk to it over HTTP, and every write carries a server-verified identity a mount could never provide. `note-origin-identity` (shipped) built the frontmatter shape this needs; this change builds the server itself.

Issue [#725](https://github.com/toejough/engram/issues/725) (multi-vault memory exchange, explicitly downstream of and building on this issue) reframes served writes from a direct pass-through into an **offer**: a write from a remote environment should not land as an immediately-committed note the way a local `engram learn`/`amend` does — it should be evaluated (covered/near/absent, the same judgment `recall`'s Step 2.5 already performs) before it's accepted, folded into an existing note, or discarded. That evaluation is inherently agent-judged (cosine only nominates candidates; the agent decides — this codebase is explicit and repeatedly documented on that point), so the server cannot make the decision synchronously inside the HTTP request. This is also a hard lesson already paid for once: an earlier `internal/server`/`internal/mcpserver` implementation (deleted 2026-04-14, "Engram is now recall-only") managed agent lifecycle (`claude -p --resume`) synchronously inside server request handling, and that reliability problem is exactly why it was torn out. This change keeps the server mechanical-only and pushes judgment back out to a skill, on the vault's existing write path.

## What Changes

- New `engram serve` command: binds to an explicit, configurable address (never defaults to `0.0.0.0`) and exposes a subset of existing CLI verbs over HTTP, reusing their existing code paths and existing vault locks — not a parallel implementation. Served: `query`, `query-chunks`, `show`, `show-chunk`, `activate`, `learn`, `amend`. Host-only (never served): `ingest`, `vocab refit`, `prune`, `check`, `update`, `resituate`.
- `ENGRAM_SERVER=http://host:port` env var on the CLI: when set, `learn`/`amend`/`query`/etc. issue HTTP requests to the server instead of touching local files — the same commands, same skills, no fork. Every remote environment still runs a full local `engram` (own embedding model, own ingest, own chunk index per issue [#720](https://github.com/toejough/engram/issues/720)'s 2026-08-17 decision) — only synthesized notes cross the API, never raw chunks/transcripts.
- Server-side identity stamping for served writes: the server authenticates the caller via Cloudflare Access (the header it injects after edge SSO) and stamps the note's `user:` field from that verified identity — a served `learn`/`amend` request's self-reported `user:` (whatever the calling instance's own git config says) is never trusted or used. `repo:` is not overridden — it carries no privilege and stays client-detected, matching how `engram amend` already behaves locally.
- Served writes do not commit immediately: `learn`/`amend` arriving over the API land as a **pending offer** (a marker on an otherwise-normal note, excluded from normal `query` results) rather than an immediately-live note. Curation — discard (covered) / fold into an existing note (near, via `amend`) / accept as new (absent) — happens later, asynchronously, off the HTTP request path, via a skill running the same covered/near/absent judgment `recall` Step 2.5 already performs, just fed pending offers instead of live query clusters. The offering side never learns the outcome (fire-and-forget).
- A stateless pending-offer detector (no persisted flag, no growth/time batching — unlike `vocab refit`'s trigger): checked at the same call sites `checkAndPersistVocabRefitTrigger` already runs from (`learn`/`amend`/`resituate`, a `LogWarning` nudge at that moment), included fresh in `engram query`'s payload every call (ambient, agent-facing — same surfacing shape as `refit_pending`, but recomputed live rather than read from persisted state), and added as a new `engram update` detect-and-notify notice (operator-facing, matching the `--backfill-identity` convention).

## Capabilities

### New Capabilities
- `vault-serve-api`: the `engram serve` HTTP server — served/host-only command split, explicit bind-address configuration, concurrency via the existing vault locks, and server-side Cloudflare-authenticated `user:` stamping for served writes.
- `vault-offer-curation`: pending-offer note marker, the stateless detector and its three surfacing points (query payload, update notice, write-path log nudge), and the async curation flow that judges offers and issues discard/amend/learn.

### Modified Capabilities
(none — `vault-note-identity`'s existing local-mode requirements are unchanged; server-mode identity resolution is new, additive behavior on a new code path, not a change to how `engram learn`/`amend` resolve identity when invoked directly)

## Impact

- New `internal/serve/` package: HTTP handlers wrapping the served command set's existing `Run*` functions, the Cloudflare-header identity adapter, and the offer-write path. Per `targ check-thin-api`, `internal/` may not call `net/http` directly — the listener is an injected adapter composed at `internal/cli`'s composition root from a raw `net/http` primitive supplied by `cmd/engram`, the same pattern as every other OS-primitive adapter (`ExecPrims`, `SpawnPrims`).
- `internal/cli/targets.go`: new `serve` subcommand; `ENGRAM_SERVER`-gated HTTP-client mode for the existing `learn`/`amend`/`query`/`query-chunks`/`show`/`show-chunk`/`activate` targets.
- `internal/cli/learn.go` / `amend.go`: pending-offer marker field on `factFrontmatterDoc`/`feedbackFrontmatterDoc`; the offer path writes this marker instead of committing a normal note.
- `internal/cli/query.go`: excludes pending-offer notes from normal results; includes the stateless pending-offer-exists flag in the payload (alongside `refit_pending`).
- `internal/cli/update.go`: new detect-and-notify detector for pending offers, following the existing five/six-detector convention (ADR-0021).
- `internal/cli/vocab_trigger.go` (or a sibling): the stateless pending-offer check, invoked from the same call sites as `checkAndPersistVocabRefitTrigger`.
- New skill (agent-instructions): the async curation flow — judges pending offers against the host vault using the same covered/near/absent reasoning `recall`'s Step 2.5 already documents, issuing `engram amend` / `engram learn` / discard. Authored under the `superpowers:writing-skills` convention as a follow-on task, not in this proposal's artifacts.
- No change to `ingest`, `vocab refit`, `prune`, `check`, `resituate` — explicitly host-only, never served.

## Open Questions

Scope-level unknowns not yet resolved (implementation-level ones — bind-address flag shape, the pending-offer marker's exact field name, curation-skill cadence, HTTP framework choice — are tracked in design.md's own Open Questions instead):

- **Does the scope/audience field ship as part of this change, as its own sibling change, or wait?** [#720](https://github.com/toejough/engram/issues/720)'s own "Decided (2026-08-17)" section names it in the same breath as origin-vault identity — "Still to fold into the note-write path while it's being built here... a scope/audience field on notes" — but it currently exists nowhere: not in `note-origin-identity` (shipped), not in this proposal. `note-origin-identity` set the precedent of splitting an [#720](https://github.com/toejough/engram/issues/720)-motivated, server-independent frontmatter addition into its own small change; this looks like the same shape. Not decided.
- **Should `engram query`'s payload expose the embedding `model_id` now?** Raised while sketching this change's API contract, not yet weighed in on. [#725](https://github.com/toejough/engram/issues/725) (downstream of this change) says its first concrete work item — rank fusion across two nodes' results — "requires the embedding model version to stay consistent across every node, or fused scores aren't comparable." Exposing it now is cheap and forward-compatible; nothing in this change would consume it yet.
