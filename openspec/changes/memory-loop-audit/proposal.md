## Why

#739's first phase was originally scoped to look only at subagent transcripts, using two narrow measurement scripts. Joe reversed that scope in review (thread `5974d361…`, 2026-08-30, on this change's own proposal): also audit the main agent's transcripts — "otherwise we don't know how well the main agent is doing at recalling relevant memories" — using one consistent scorecard that covers the whole memory loop, including the times it works, not just the times it fails. ADR-0028 (accepted 2026-08-30) generalizes that reversal: engram is meant to be the layer that lets a fixed-weight LLM learn from experience, and this audit is the missing piece of that loop — the step that looks back at what happened and labels it a win or a loss. This change builds that measurement tool as something we can run repeatedly (not a one-off script), runs it for the first time, and produces the go/no-go decision that #739's second phase (having the orchestrator hand matched memories to subagents, and having subagents report lessons back) is waiting on. It restores the wider 2026-06-28 scope (main agent and subagents, across every repo) and widens what counts as worth measuring from "failures only" to the whole loop.

## What Changes

- **Mechanical extractor** (`dev/eval/audit/`, Python, unit-tested): reads Claude Code and Pi transcript files and pulls out, for each one, a structured list of what happened — every memory search that ran (the phrases used, and what came back), every subagent dispatch (the prompt, whether it was a fork/fresh-context/workflow subagent, which notes were included), every learn/write-memory skill call, every `engram learn/amend/activate` command, and every completion report. This runs over every transcript with no LLM calls, and is written so it can later be promoted into a real `engram audit` command without redoing the design work (ADR-0028 D5).
- **Semantic auditor** (LLM-based, run on a sample): reads a transcript in windows and identifies the interesting moments — failures, corrections, rework, **successes**, and **subagent dispatches** — then answers the judgment questions from ADR-0028's scoring model (see design.md) for each one, and joins that with the mechanical extractor's output into one record per moment. Detection is tuned to over-flag and then discard, its miss rate is measured against hand-labeled examples before any real run, and a person reads a sample of the output by hand before any money is spent on the full run.
- **Point-in-time memory check**: for each moment, the tool writes its own search phrases and asks "did a relevant memory already exist in the vault at that moment?" — checked against a read-only copy of the vault at the last commit before that moment (an exact answer, labeled DERIVED), falling back to filtering notes by their creation date when git history isn't available (an approximate answer, labeled ESTIMATE); for the auto-ingested chunk index, it filters by ingestion date instead. This reads the vault (via a read-only checkout) but never writes to the live vault, and runs under the existing test-isolation setup (#708).
- **Draft outcome records**: for each (moment, memory) pair, a small file noting whether that memory helped, hurt, was ignored, or was missing when it should have existed, with a pointer to the evidence. These land under `dev/eval/audit/results/`, alongside the tool's other output — not near the vault itself; unlike `engram serve`'s pending offers, these are dev-eval tool output, not vault content. This change only produces these files — deciding what to actually do with them (updating, superseding, or retiring notes) is a separate follow-on change.
- **First measurement + report**: the per-moment scorecard, with every rate reported against a counting unit that was fixed before the numbers existed, and every number labeled DERIVED or ESTIMATE; the slice of results specific to #739; a pass over the leftover unresolved moments that groups them and drafts a fix for each group (as vault notes by default, and as repo issues only where a note genuinely can't reach the problem); new rows in `dev/eval/LEDGER.md` plus a first version of the coverage-map index.
- **Go/no-go decision**: the pass/fail thresholds are agreed and written down before the full run happens; the resulting green/yellow/red decision is recorded on #739.

**Out of scope:** the audit writing anything to the vault (its output records are just data); a full experience-record system; replay/mining modes; turning this into a real `engram audit` command; any change to production code, skills, or agent guidance; #739's second phase itself.

## Capabilities

### New Capabilities

- `memory-loop-audit`: the requirements any tool measuring the memory loop against real transcripts must meet — detecting moments (including successes and dispatches) by reading them in context rather than by keyword matching; producing a complete per-moment record with a fixed counting unit and a DERIVED/ESTIMATE label on every number; the point-in-time memory check described above; treating memories that were put directly into a subagent's prompt as "found"; only emitting draft outcome records, never acting on them; thresholds agreed before the run; and recording results in the shared ledger and coverage-map index.

This change absorbs two earlier, never-finished proposals (`subagent-correction-detection`, `delegation-dispatch-handoff-audit`): their detection logic, miss-rate checks, and calibration approach carry over as requirements here. The old rule that skipped forked subagents entirely is replaced by treating anything handed to a subagent (forked or not) as "found."

## Impact

- A new, reusable measurement tool lives under `dev/eval/audit/`; no production code, skill, or guidance changes.
- `dev/eval/LEDGER.md` gets new dated rows plus a new coverage-map index section (nothing existing is renamed or removed).
- Read-only against real transcripts and the real vault (the point-in-time check uses read-only git checkouts; every tool invocation runs under the #708 test-isolation setup).
- Once done: #739's description gets rewritten as one current summary with its second phase marked as waiting on this gate (vault note 819); two follow-on issues get filed (one for acting on the outcome records, one for the replay/mining modes); #718 gets narrowed in scope; #742 gets a note added — all per ADR-0028's consequences.
