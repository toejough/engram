## Context

ADR-0028 (2026-08-30) sets the overall design for turning agent experience into memory updates: a standing tool with three modes (watch what already happened, replay it, or mine it for training data); a per-moment scorecard; only acting on results a person has judged, never automatically; experience tied to the situation it came from; building it first as a dev-only Python tool rather than product code; measuring behavior against the version of the skill/guidance that was actually in effect at the time; retiring the old build-cost harness in favor of the shared ledger; and hard-gating #739's second phase on this audit. This change builds only the "watch what already happened" mode, plus runs the first measurement.

Relevant existing state:

- A deleted 2026-06-28 doc (`git show d425a153^:docs/design/2026-06-28-failure-eval-material.md`) mined transcripts for failures the same way this change will, and is the closest precedent: 40 transcripts (25 subagent + 15 main, across 5 repos), a haiku-based auditor, semantic detection tuned to over-flag and then discard, a measured miss rate, 137 confirmed records, with columns for coverage, failure category, and where the ideal fix belongs. This change rebuilds that tool with a scorecard covering the whole loop, including success moments, not just failures.
- `engram ingest --auto` already scans main and subagent transcripts; each chunk it produces records when it was ingested, which the point-in-time check uses to decide whether a chunk existed yet at a given moment.
- The vault is a git repo (Joe confirmed this 2026-08-30), so the exact point-in-time check is possible today; how far back it works depends on how often commits were made — sparse early history means older moments fall back to the approximate check, and we won't backfill history to fix that.
- `dev/eval/isolation.py` (#708) already provides the sandboxing every engram command in this tool needs to run under.
- Two decisions from the prior version of this proposal carry over unchanged: Phase 2's memory-injection point belongs to `delegate.md` (note 855), and giving every subagent its own full memory loop is parked, not rejected (route record 429).

## Goals / Non-Goals

**Goals:** build the watch-mode tool (the mechanical extractor, the semantic auditor, and the point-in-time check); run the first measurement across all repos, over both main-agent and subagent transcripts; produce the labeled per-moment scorecard, the #739-specific results, the draft outcome-record files, the grouped-and-drafted fixes for leftover gaps, and the ledger rows plus coverage-map index; and decide the pre-agreed go/no-go gate for Phase 2.

**Non-Goals:** acting on the outcome records or writing to the vault in any way; a full experience-record system (`.exp.json`); replay or mining modes; a real `engram audit` command; editing `delegate.md`, `learn.md`, `recall.md`, or any skill file; actually running `/learn` or `/recall` live as part of measuring (this reads past transcripts, it doesn't re-run them); building Phase 2 itself.

## Decisions

- **D-A — What transcripts we look at:** main-agent and subagent transcripts across every one of Joe's active repos (Claude Code's `~/.claude/projects/<repo>/…` main session files, plus `<session>/subagents/**` including workflow subagents; Pi's equivalent paths are checked live, falling back to Claude-Code-only with a documented reason if they don't exist). We take a representative sample sized so one agent can read each piece in one pass; sessions over 500 KB get split into windows, because a second calibration round measured that no single agent reliably reads a 570 KB session all the way through. Each window is at most 150 KB, split at natural turn boundaries (matching the 8-180 KB window sizes used in the 2026-06-28 sample), and the boundaries are written down. Sample size and how it's split are recorded before any money is spent on LLM calls. Why sample across every repo rather than one: sampling from a single repo skewed a past measurement the wrong way (vault note `feedback_verify_mined_corpus_is_representative`).
- **D-B — Two tools, two scopes:** the mechanical extractor runs over the **entire corpus** (so counts and rates are based on real totals, never guesses — runbook 824); the LLM-based auditor only runs over the **sampled** windows. The two are joined by matching transcript and location. Detection follows vault note 112's finding that most corrections are subtle (word-matching alone misses about two-thirds of them): it's tuned to over-flag and then discard, and its quality bar is how many real moments it misses when checked against hand-labeled examples — flagging too much is fine, missing real moments is not. The auditor runs as an automated `claude -p` process under an isolated config directory (the same approach already used elsewhere in `dev/eval` — no separate API key needed); wherever a test uses a stub, that means a canned reply with no real network call. Following the 2026-06-28 precedent: the cheap haiku model does detection (a second calibration round showed it matches the more expensive sonnet model 5 out of 5 times at this window size); a stricter sonnet model re-checks any window that yielded suspiciously few findings; and sonnet also answers the judgment questions for moments that were found. Success moments — a case where a memory the agent had was clearly used and helped — get treated as full citizens here, not an afterthought, since they're the "this worked, reinforce it" half of ADR-0028's loop, matching the learn skill's existing idea of a confirmed-approach note.
- **D-C — The point-in-time memory check:** the auditor writes its own search phrases for each moment, based on what actually happened (separately, it also checks whether the *agent's own* search phrases at the time would have found the right thing — that's the "did the search target the right thing" question, judged on its own). For notes: check a temporary, read-only copy of the vault at the last commit before that moment — call this an exact (DERIVED) answer. If the vault didn't have git history yet, or the moment predates that history, fall back to filtering notes by creation date instead — call this an approximate (ESTIMATE) answer, and flag that any edits made to a note after the moment won't show up in this fallback. For chunks: filter by their ingestion date, which is always an exact (DERIVED) answer. Every one of these checks runs under the #708 sandboxing, the temporary copies are always cleaned up afterward, and the real vault is never modified.
- **D-D — What each moment's record contains** (this is the per-moment scorecard ADR-0028 calls for): identifying info (which transcript, where in it, when, which repo, which harness, main-agent-or-subagent, and dispatch type); the moment's type (failure, correction, rework, success, or dispatch); a short description and a pointer to the evidence; on the finding-a-memory side — did a relevant memory exist (and if so what kind: chunk, fact, feedback, runbook, or qa; whether it was generic or specific to this situation; and whether that existence check was DERIVED or ESTIMATE), did a search actually run (a quick glance, a full recall, an injected prompt, or none), did the search target the right thing, was it surfaced (and at what rank, and whether an outdated note out-ranked its replacement), and was it followed (or if not, how it deviated: ignored, partially followed, a step skipped, steps done out of order, or contradicted); on the writing-it-down side — was this a moment worth learning from, did a learn step actually fire, did a note get written (and was it well-targeted, did it correctly supersede an old note, was it not a duplicate), and was the used note's strength updated (with any mismatch flagged); and for the boundary between agents — which memories were actually handed to a subagent, and for dispatch moments specifically, which ones the orchestrator had but didn't hand over. Each record also gets a failure category from runbook 824. Dispatch type is decided by a simple, non-judgment rule: if the parent's tool call says `subagent_type == "fork"`, it's a fork; if the transcript lives under `subagents/workflows/**`, it's a workflow; otherwise it's a fresh-context subagent — cross-checked by looking for the fork boilerplate text at the start of the subagent's transcript.
- **D-E — A memory in the dispatch prompt counts as found** (Joe's rule): if a subagent's prompt already contains a memory, that counts as "a search ran and it was found," because the orchestrator did the finding on the subagent's behalf. Forked subagents inherit the whole parent conversation, so everything in it counts as found for them automatically. The gap on the finding side — memories the orchestrator had but didn't pass along — is measured from the orchestrator's side, at the moment of dispatch, by comparing what it had against what it actually included. This replaces the old approach of excluding forks from the count entirely.
- **D-F — The outcome-record format (output only, nothing reads it yet):** one JSON line per (moment, note) pair, recording the moment, the note, the situation, an outcome tag (helped, hurt, was surfaced but ignored, was handed to a subagent but not used, or should-have-existed-but-didn't), a timestamp, and a pointer to the evidence. Written to `dev/eval/audit/results/`, next to the tool's other output files — not near the vault; unlike `engram serve`'s pending offers, this is dev-eval tool output, not vault content, and nothing about it touches the vault's own storage. The should-have-existed-but-didn't case is exactly the input to the leftover-gaps pass below. Nothing in this change consumes these records — they're a contract that the follow-on change (which decides what to actually do with them) will be built against.
- **D-G — Deciding the pass/fail bar before running the real thing:** before the full run happens, we commit in writing to (a) the counting unit for each rate — mainly per-moment, with per-dispatch and per-transcript as secondary views, (b) the actual thresholds for the Phase 2 go/no-go decision — on the writing side, what fraction of lost lessons a completion-report step could realistically catch; on the finding side, what fraction of dispatch-time losses a prompt-injection step could realistically catch — and (c) what result maps to green, yellow, or red. All of this gets decided before we've seen any real numbers, so we can't unconsciously pick thresholds that flatter the result.
- **D-H — Built as a Python dev tool first, not product code:** what #739 is waiting on is the measurement itself, not a polished feature — and evaluation tooling like this belongs in `dev/eval` under the existing product/dev-tooling split. Turning it into a proper `engram audit` command (with dependency injection, following the CLI's usual conventions, etc.) happens later, in the follow-on change, built against this change's requirements (which are written to not assume Python).
- **D-I — What gets produced, and where fixes for leftover gaps go:** the per-moment records and the outcome records, both as JSONL files; a written-up report (a table of results with each one labeled, plus a short write-up per major finding); one ledger row per claim, each pointing at its raw data; and a new coverage-map index section in the ledger (which memory function, by which kind of note, is backed by which rows and what measured rate) — added without touching any existing ledger row. For the leftover unresolved moments, fixes are proposed using a simple two-step rule (vault note 495): first choice is always "write or update a vault note — the user owns their vault, and the fix takes effect the next time they recall" — that covers most cases. Only fall back to "change engram's code, a skill, or its shipped guidance" when a vault note genuinely can't reach the problem, per vault note 803's test: would a note describing the fix ever actually get retrieved at the moment the bug happens, given what gets searched for at that point in the procedure? If what's being searched for is about the task at hand rather than the procedure itself, a note has no way to surface there, and only a real code/skill/guidance change will fix it.
- **D-J — Joe signs off before anything durable gets written:** the measured results and the resulting go/no-go decision get shown to Joe before any ledger rows are written or #739/#718/#742 get updated (same precedent as the #642 plan's rule about gating durable-record changes).
- **D-K — Where this actually runs:** the tool itself is built and unit-tested in the dev sandbox, against made-up test transcripts. But finding the real transcripts (tasks 1.x) and running the real measurement (tasks 5.x) happen on Joe's own machine, where the real multi-repo transcript history and the actual git-tracked vault live. A dev sandbox — one repo's worth of transcripts, no local vault, talking to a remote vault — is not good enough to measure from: sampling from just one repo has skewed a result before (see D-A), and there's no local vault history for the point-in-time check to look at anyway. The tool ships through GitHub as usual; Joe pulls it and runs it on the host.

## Risks / Trade-offs

- [The LLM-based auditor could get expensive] → the full corpus only goes through the free mechanical extractor; LLM spend is limited to the sample plus calibration, with cost confirmed before the real run (roughly $20-50 at 2026-06-28's scale).
- [The detector could undercount subtle moments] → the same miss-rate gate and conservative labeling used in the 2026-06-28 precedent, plus a stricter model re-checking any window that turned up suspiciously little.
- [The scoring logic itself could have bugs] → at least 3 transcripts get hand-read against the scoring logic before any money is spent (vault note 505: a past keyword-based scorer once falsely fired on table headers — hand-reading is the only way to catch that kind of thing before spending on a full run).
- [The point-in-time check is coarse where the vault has few old commits] → every number is labeled DERIVED or ESTIMATE so this is visible rather than hidden, and we're not backfilling git history to fix it (ADR-0028 D6).
- [Pi transcripts might not exist or might be shaped differently] → falls back to Claude-Code-only with a documented reason (D-A); the requirements themselves don't assume any particular tool.
- [Risk of quietly expanding scope into acting on the outcome records] → explicitly out of scope; only the record format itself is part of this change.

## Open Questions

- The exact pass/fail thresholds and sample sizes — these get decided during the pre-registration task, based on what the actual transcript inventory looks like, not fixed here.
- How often the vault was committed to before roughly August 2026 — this determines how much of the corpus gets the exact (DERIVED) point-in-time answer versus the approximate (ESTIMATE) one; it gets measured in task 1.3 rather than assumed.
