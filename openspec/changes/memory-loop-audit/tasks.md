## 1. Corpus discovery and preconditions

> Where these run (see design.md D-K): tasks 1.x and 5.x need the real transcripts and the real vault, so they run on Joe's machine (the host). Tasks 2.x-3.x build and test the tool itself and can run anywhere — except their real-data checks (2.2, 3.2's live-vault check, 3.3's hand-labeled examples), which also need the host's real data.

- [ ] 1.1 Confirm where the real transcripts actually live — don't assume, check: (a) Claude Code — main session `.jsonl` files under `~/.claude/projects/<repo-path>/`, subagent transcripts under `<session-id>/subagents/**`, including workflow subagents under `subagents/workflows/**`; (b) Pi — look under `~/.pi/` for an equivalent layout and write down what's actually there, or write down that it's absent and scope this change to Claude Code only (see design.md D-A). Done when: a checked-in inventory file (`dev/eval/audit/corpus.json`) lists every location found, with counts of main and subagent transcripts per repo.
- [ ] 1.2 Sort and sample the transcripts: group them by repo, by main-agent-vs-subagent, by dispatch type (fork/fresh/workflow, read from the transcript itself), and by size; then decide the representative sample and how oversized sessions (500 KB+) get split into windows (see design.md D-A). Done when: the inventory file records the total counts, how many were sampled from each group, and the window boundaries chosen for each large session.
- [ ] 1.3 Confirm the point-in-time check can actually work: (a) confirm the vault is a git repo, and record its first and last commit dates and how often it was committed to — that tells us how much of the corpus's time range gets the exact (DERIVED) answer versus the approximate (ESTIMATE) one for moments that predate dense history; (b) confirm chunk records really do carry an ingestion timestamp, by pointing at the actual field in `internal/chunk/` as it exists right now. Done when: the inventory file has a section with the commit-frequency table and the code reference.

## 2. Mechanical extractor (full corpus, no LLM)

- [ ] 2.1 Build `dev/eval/audit/extract.py`, with unit tests against small, made-up example transcripts checked into the repo. For each transcript, it should pull out: recall calls (the Skill call plus the `engram query` result, parsed into phrases and matched items with their path/kind/source/rank), dispatch events (Agent tool calls: the prompt text, subagent type, and model), learn/write-memory Skill calls, `engram learn|amend|activate` commands, and completion reports. The example transcripts need to cover: a main session with a recall and a dispatch, a forked subagent, a fresh-context subagent, and a workflow agent. Done when: `pytest dev/eval/audit/` passes (note: if `pytest` isn't installed, bootstrap it with `python3 -m ensurepip` then pip; task 3.2's point-in-time check may need `go` explicitly on the PATH before `go install ./cmd/engram` works).
- [ ] 2.2 Check the extractor by hand against at least 2 REAL transcripts (one main session with at least one recall and one dispatch, one subagent transcript): read the raw file yourself and compare it to what the extractor produced; fix any mismatches; write down what you compared. Do this for every dispatch type that actually shows up in the real corpus — if the workflow type only exists in the made-up fixtures until the real run happens, say so in the write-up. The point is to check a measurement against the real thing it's supposed to describe, not just against itself (vault note 478). Done when: the comparison write-up is checked in next to the tests.
- [ ] 2.3 Add Pi transcript support to the extractor, or, if 1.1(b) found Pi transcripts don't exist, carry that documented exclusion into the inventory file.

## 3. Semantic auditor (sampled windows)

- [ ] 3.1 Build the auditor's prompt and runner script (`dev/eval/audit/audit_moments.py`): split into windows per task 1.2; detect every moment type from design.md D-D (failure / correction / rework / SUCCESS / DISPATCH — successes matter just as much as failures, not an afterthought); answer the scorecard questions for each one; over-flag first and let the model itself discard non-moments; and write out one JSONL record per moment, joined to the mechanical extractor's events by transcript and location. Done when: the runner works end-to-end on one example window using a stubbed model (a canned reply, no real network call); real runs use the automated `claude -p` process at the model tiers decided in design.md D-B (haiku for detection, sonnet for re-checking low-yield windows, sonnet for answering the judgment questions).
- [ ] 3.2 Add the point-in-time check inside the runner: come up with search phrases for each moment; build the as-of-that-moment set of notes (a temporary, read-only git checkout at the last commit before the moment, always cleaned up afterward) and chunks (filtered by ingestion date); run `engram query` under the existing `dev/eval/isolation.py` sandboxing (#708 — confirm isolation before every call); judge whether a relevant memory existed, what kind it was, and whether it was generic or specific to the situation; and label each record's answer DERIVED or ESTIMATE per design.md D-C. Done when: a test proves the sandboxing works (an empty scratch vault returns zero results), and a trial run is shown not to have changed the real vault at all.
- [ ] 3.3 Calibrate BEFORE running the real thing: hand-label a representative sample of 10-20 windows (covering both main-agent and subagent, across at least 2 repos — this needs the real host data, see D-K; a single-repo dev sandbox can't satisfy it); measure how many real moments the detector missed compared to those hand labels; write down, in advance, the miss-rate the full run has to meet; and run the stricter re-check on any low-yield windows, following the 2026-06-28 precedent. Then hand-read at least 3 full trial outputs against the scoring and joining logic (vault note 505: this kind of check only tells you anything before the results start looking legitimate). Done when: the calibration data and the pre-agreed miss-rate tolerance are both committed before task 5 starts.

## 4. Agreeing on the pass/fail bar (all before the full run — the order matters)

- [ ] 4.1 Fix the counting unit for each rate before computing anything: mainly per-moment, with per-dispatch (for the finding-side gap) and per-transcript as secondary views. Write these into the report template.
- [ ] 4.2 Agree on the Phase 2 go/no-go thresholds, in writing, before seeing real results: on the writing side, what fraction of lost lessons a "write your lessons in the completion report" step could realistically catch; on the finding side, what fraction of dispatch-time losses a "hand the subagent the matched notes" step could realistically catch; and what result counts as green, yellow, or red, and what happens in each case (green: go ahead and build Phase 2; yellow/red: revise the scope, and say how). Process: draft the thresholds with a short reason for each, show them to Joe, and only commit them once he approves — task 5 must never run against thresholds he hasn't signed off on. Commit this before task 5 starts.
- [ ] 4.3 Estimate what the full run will cost in LLM spend, based on the calibration runs; confirm that estimate with Joe; then run the full thing without stopping partway to check the budget.

## 5. Full run

- [ ] 5.1 Run the mechanical extractor over the ENTIRE corpus; run the LLM auditor over the agreed-on sample; join the two together. Save the raw output under `dev/eval/audit/results/` (one JSONL file of per-moment records, one of per-transcript events).
- [ ] 5.2 Compute the results: the loss rate at each stage of the per-moment scorecard, using the counting units fixed in task 4.1; a breakdown by failure category per runbook 824; a breakdown by memory kind and generic-vs-specific; a per-repo breakdown (to check for the single-repo skew risk from D-A); every number labeled DERIVED or ESTIMATE. Also compute the #739-specific slice: on the writing side, how many lessons were lost and what fraction of those are realistically reachable; on the finding side, the gap between what the orchestrator had and what it actually handed to subagents (with forks always counted as "handed over," per design.md D-E).
- [ ] 5.3 Write out the outcome-record JSONL file per design.md D-F, plus a short doc (`dev/eval/audit/CREDIT_SCHEMA.md`) describing its format, which the follow-on change will build against. No vault writes of any kind.
- [ ] 5.4 Collect the leftover unresolved moments (the ones marked as "nothing could have caught this" or "no cue exists to trigger this"), group similar ones together, and draft a fix for each group following the note-495 rule — a vault-note fix by default, and a repo-change proposal only where the note-803 test says a note genuinely can't reach the problem (that is, actual bugs in how a procedure runs). Output: a proposals section in the report — don't file any actual issues yet.
