## Context

Between 2026-09-19 and 2026-09-22, four skills were converted to vault runbooks by deleting their `SKILL.md` and promoting a note to Joe's personal vault: route (`87e9a006`), please (`b79f390e`), curate (`2c4c2637`), write-memory (`a81f7edc`). Each conversion's proposal recorded "engram update stops shipping the X directory" under Impact as if neutral. It was not: `engram update` (`internal/update/update.go`, `planAndApply` :1161 → `planSkillCopies` :2380) syncs `agent-instructions/skills/` and `guidance/` into harness dirs and **never touches the vault** (stated at :300–302, :318–319, :341–343). Vault notes are not distributed. A fresh install today ships only `learn` and `recall` (verified: `~/.claude/engram/skills/` holds exactly those two). Vault note 1054 records the reversal; it refutes note 1031's "every skill becomes a runbook; the shim is the only custom CLAUDE.md text."

Two in-flight changes (`learn-skill-to-runbook`, `recall-glance-skill-to-runbook`) were about to repeat the pattern; neither reached a paid run. Their validated metadata (situation lines, triggers scored against over-fire probes, red_flags under the 1200-byte cap, sub-runbook splits, eval fixtures with mutant-tested checkers) is the authored input this change needs and is not discarded.

Facts that constrain the design (all verified in code):
- **No Go code parses `SKILL.md`.** `planSkillCopies` copies skills as opaque bytes. Frontmatter today is exactly `name:` and `description:`. A parser is new work; the only frontmatter parsers in `internal/` are vault-note ones (`internal/embed/hash.go` `ExtractBody` :67; `internal/cli/amend.go` yaml unmarshal).
- **No create-or-update mechanism exists for notes.** `deps.WriteNew` is `WriteFileExcl` (exclusive create, `deps_compose.go:180`); `engram amend` resolves `--target` only by exact Luhmann id or basename (`findNote`, `resituate.go:144`); offers are keyed by nothing but a `pending: true` marker (`offer.go:84`). Luhmann ids come from `nextTopLevel` (`luhmann.go:162`, max existing + 1) — order-dependent, not derivable from a skill's identity — and basenames embed date + id. An idempotent upsert must locate the existing derived note **by a frontmatter field**, never by a predictable path.
- **The vault-mutating step of update already exists one layer up.** `internal/cli/update.go:runPostUpdateChecks` (:458) resolves the vault path and runs vocab regen, identity backfill, and Luhmann reparenting with `cli.Deps` (which provides `newLearnDeps`/`newAmendDeps`: lock, FS, embedder). Registration hooks in there.
- **Sharing already works for surfacing, not for following.** A parent-vault runbook reaches a client's `engram query` under `ENGRAM_PARENT` (`merged_query.go:100,177`; `splitTriggerItems` :111 places parent trigger hits first; items tagged `from_parent`). But `engram show <basename>` is local-only unless `--parent` is passed explicitly (`show.go:19-23`; spec `vault-merged-recall` :135). The shim's follow-frame emits `engram show <basename>` with no `--parent`, so a shared runbook surfaces and then cannot be followed.
- **`please` is four notes** (1045 + 1042/1043/1044); `recall`'s decided shape is two entry points sharing sub-runbooks. One `SKILL.md` frontmatter block cannot express a multi-note runbook, and body wikilinks between the notes need basenames that don't exist until derivation.
- **Nine call sites in `recall`/`learn` and write-memory's last red_flag** say the write-memory skill "no longer exists" and instruct `engram show 1053…` instead — true only while the skill is deleted. The write-memory eval's skill-arm baseline (invoked natively as a skill by recall/learn) was 3/3 followed_all, 3/3 end_state (`results/1.4_write_memory_skill_baseline_sonnet5.md`).
- `engram update` deploys are syncs, not additive copies (vault note 442): removals propagate.

## Goals / Non-Goals

**Goals:**
- Restore distribution: every engram install ships all six skills again, via the existing `engram update` mechanism, with no new distribution machinery.
- Keep everything the runbook work bought (memory-driven surfacing by situation/trigger, the follow-frame, cross-vault sharing) by registering skills as derived runbook notes.
- One source of truth per procedure (the skill file), one authoring surface (its frontmatter), zero drift (mechanical re-derivation on update).
- Carry forward every validated conversion artifact as registration input.

**Non-Goals:**
- Registering skills engram doesn't ship (the 27 user/plugin skills in `~/.claude/skills/`). Named follow-on.
- Retiring `guidance/{recall,learn,delegate}.md`. Named follow-on.
- Any new distribution mechanism for vault notes. The point is that skills already have one.
- Changing how any skill's procedure actually works.
- Re-running the paid recall/learn evals. Their metadata is adopted as authored; retrieval is re-checked at no cost.

## Decisions

**D1. The skill file is the single source of truth; the vault runbook is a derived mirror.** Alternatives: (a) keep runbooks canonical and invent a note-distribution mechanism — rejected, it duplicates a mechanism that exists and re-solves sync/removal/symlink problems already solved for skills; (b) "search returns skills" without a runbook representation — rejected, a returned skill body is prose the agent interprets fresh, while a runbook carries `done_when`/`red_flags`/`triggers` the shim's follow-frame drives (the please eval measured this: skill row 0/3 followed_all vs triggered runbook 3/3). Registration keeps distribution AND the schema.

**D2. Runbook metadata lives in the skill's own frontmatter; registration is opt-in by authoring it.** `SKILL.md` frontmatter gains `situation`, `triggers`, `done_when`, `red_flags` (same semantics and limits as the runbook note: red_flags ≤ 1200 bytes rendered, triggers whole-word matched). A skill with these fields is registered; one without (`name` + `description` only) deploys as today and never enters the vault. Alternative: an explicit `register: true` flag — rejected as redundant; authoring the fields *is* the intent, and a flag adds a second thing to keep consistent. The metadata was the hard, judgment-heavy, eval-validated part of every conversion (please's situation line took three rewrites plus a shim change; triggers needed over-fire scoring), so it must be authored, never inferred from prose.

**D3. Identity and upsert: a `registered_from:` frontmatter field on the derived note, scanned at registration.** Value is `<skill-name>/<runbook-slug>` (top runbook: `<skill-name>/SKILL`). Registration: for each registered runbook, scan the vault for a note whose `registered_from` matches → `amend` it (replace-whole for every derived field: situation, done_when, red_flags, triggers, body); none → `learn runbook` (fresh Luhmann id, normal basename). `created` is preserved on amend; `source` records the skill path and the deploy that derived it. Alternatives: (a) deterministic basenames — rejected, breaks the Luhmann/date basename convention every other note follows (`learn-runbook-capture` requires runbooks to participate in the hierarchy); (b) matching by `source:` prose — rejected, fragile. The existing promoted notes (1036, 1045, 1042–1044, 1049, 1053) are **adopted** on first registration by stamping `registered_from` onto them (an amend), not re-created — preserving their ids, wikilinks already in circulation, and history.

**D4. Registration is a sync.** A derived note whose `registered_from` no longer corresponds to a registered skill is removed on update (vault note 442). A derived note is a mirror, not memory; git holds the vault's history if a removal is ever wrong. `engram amend` on a registered note's derived fields is allowed but overwritten on the next registration — the note carries a one-line body preamble saying so, and the amend path warns when the target has `registered_from`. Alternative: reject amends on registered notes — rejected as too rigid for one-off local experiments; overwrite-on-sync is the honest semantic.

**D5. Multi-runbook skills: one file per runbook inside the skill directory.** `SKILL.md` is the top/entry runbook; `runbooks/<slug>.md` are the subs, each with its own runbook frontmatter. For `recall`'s two-entry-point shape, `SKILL.md` is `recall-glance`... no — both entry points are peers, so `recall` uses `runbooks/glance.md` and `runbooks/deep.md` as the two registered entry points, with `SKILL.md` carrying the mode-selection description only (not itself registered as a runbook — it has no single situation). Cross-references are authored as stable skill-local slugs (`[[please/adversarial-review-gates]]`, `[[recall/core]]`) and rewritten to the real derived basenames at registration, which creates/updates all of a skill's notes together and therefore knows the mapping. Alternatives: (a) a `sub_runbooks:` array inside one frontmatter block — rejected, unreadable at please's size and hostile to per-sub red_flags budgets; (b) `##` sections mapped to subs — rejected, couples registration to prose structure. Wikilinks between registered notes therefore always resolve; a dangling skill-local slug is a registration error, not a silent WARN.

**D6. Restore the four skills from their last intact commits and revert deletion-only wording.** route from `f5b44504` (incl. `price-table.md`, `tests/`), please from `ec5f3735`, curate from `14049280`, write-memory from `cbda7f6e`, then add frontmatter lifted verbatim from each promoted note. The nine `recall`/`learn` call sites revert to native skill invocation of write-memory (the proven 3/3 path); write-memory's "no longer exists as a skill" red_flag is dropped; `please`'s body is split into `SKILL.md` + three `runbooks/*.md` matching 1045/1042/1043/1044 with slug cross-references. `learn`'s Step 2.5 duplicate-guard fix (already live in the real skill) is kept.

**D7. `engram show` falls back to the parent on a local miss when `ENGRAM_PARENT` is set.** Today only `--parent` reaches the parent. The shim's follow-frame cannot be told to add `--parent` selectively (it doesn't know where a surfaced note came from — though items are tagged `from_parent`, the frame's instruction is a bare `engram show <basename>`). Fallback-on-miss is transparent, needs no shim change, and mirrors merged query's existing local-then-parent behavior. `ENGRAM_SERVER` precedence and the explicit `--parent` flag are unchanged. Sequenced last (see Migration Plan) so registration + restoration can ship first and this can be split off if the change grows too large.

**D8. Abandon, don't archive, the two delete-conversion changes.** OpenSpec has no "abandoned" state; the change directories are removed with a commit whose message records why and where their artifacts were carried (the fixture vaults and fidelity reports under `dev/eval/` stay; the recall/learn frontmatter is authored from them). Git preserves the full change history. Alternative: archive them as complete — rejected, they weren't, and archiving would sync their delta specs (which assert the skills are retired) into the main specs.

**D9. No paid eval for the mechanism.** Registration is mechanical (parse → upsert → embed) and fully unit-testable with DI fakes; the retrieval properties of the restored skills were already validated on the identical metadata. Re-run a retrieval check (no spend) for each registered skill after adoption to confirm the derived notes surface exactly as the promoted notes did. A paid re-validation is warranted only if metadata is changed during restoration.

## Risks / Trade-offs

- **[Risk] Drift between skill and derived note between updates.** → Registration runs on every `engram update` and is idempotent; a `registered_from` note is marked derived in its body. Residual: an edit to the skill file with no `engram update` afterward — same class as any un-deployed skill edit today.
- **[Risk] Adopting existing notes by stamping `registered_from` could mis-adopt if a note's content diverged from the restored skill.** → Restoration lifts frontmatter FROM the promoted notes, so on first registration skill and note agree by construction; the fidelity check in tasks compares them field-by-field before stamping.
- **[Risk] Slug cross-reference rewriting is a new transform with its own failure modes (a slug that matches nothing; a rewrite that touches prose it shouldn't).** → Slugs are namespaced (`<skill>/<slug>`), only `[[...]]` tokens matching a registered slug of the same skill are rewritten, unresolved slugs fail registration loudly, and the transform is property-tested (round-trip; no-op on non-slug wikilinks).
- **[Risk] `show` parent fallback changes the meaning of a local miss (previously an error).** → Only when `ENGRAM_PARENT` is set; the fallback result is labeled as parent-sourced in output; explicit `--parent`/`ENGRAM_SERVER` semantics unchanged and tested.
- **[Trade-off] This change is large (parser, upsert, sync, multi-runbook, four restorations, docs/spec reversals, two abandonments, show fallback).** → Sequenced so registration + restoration land first as a coherent unit; D7 and the doc enumeration are the natural split points if needed.
- **[Risk] Doc/spec surface is the widest yet** — every conversion's "retired" language plus the reversed end goal in `guidance-runbook-follow-frame`'s Purpose, ADR-0026's amendment, GLOSSARY, CLAUDE.md, README, ROADMAP "Shipped" rows. → The doc-surface enumeration gate with an independent fresh-context reviewer, as every conversion used; Purpose-line edits become archive-time tasks (a delta cannot edit Purpose).

## Migration Plan

1. Parser + registration command + upsert-by-identity + sync removal, TDD with DI fakes; hook into `runPostUpdateChecks`.
2. Restore the four skills with frontmatter; split `please` into `SKILL.md` + `runbooks/`; revert the nine call sites and write-memory's stale red_flag.
3. First registration adopts the existing promoted notes (stamp `registered_from`, verify field equality); `engram embed status` clean; retrieval checks (no spend) confirm the derived notes surface as before.
4. Author `recall`'s and `learn`'s frontmatter from their fixture runbooks; register them; retrieval checks.
5. Abandon the two delete-conversion changes (D8).
6. `show` parent fallback (D7) with tests, incl. a merged-vault smoke: a runbook present only in a parent is surfaced by `engram query` and then fetched by bare `engram show`.
7. Doc-surface enumeration + independent review; perform every row; archive-time Purpose edits recorded as tasks.
8. `engram update --with-guidance` on this machine; verify all six skills deployed in both harnesses and all registered notes present; `targ check-full`; commit; archive.

Rollback: revert the commit(s); derived notes carry `registered_from` and can be removed by the sync (or by hand from git); restored skills are plain files.

## Open Questions

- The exact command surface: `engram register-skills [--dry-run]` as a standalone command vs. only an update hook. Default: both (the standalone command is what the update hook calls, and is what a developer runs after editing a skill locally).
