## Context

See `proposal.md` - Why. Relevant existing shape, verified against code:

- `internal/cli` is DI-everywhere: no function calls `os.*`/`exec.*` directly; every capability is injected via `cli.Primitives` → `cli.Deps` at the `internal/cli` composition root, wired from raw primitives supplied only by `cmd/engram` (`targ check-thin-api`-enforced).
- `Getwd func() (string, error)` is already an injected primitive (`internal/cli/primitives.go:98`), already consumed by `ingest.go:707` to resolve the working directory for session-sweep discovery.
- `Commander`/`RunCommand` (`internal/cli/commander.go`, `primitives.go:17`) already shells out to external commands via `exec.CommandContext`, currently wired only into `internal/update`'s git-based self-update deploy sync. It captures stdout/stderr and translates a not-found error to `update.ErrCommandNotFound`.
- `factFrontmatterDoc`/`feedbackFrontmatterDoc` (`learn.go:142-191`) are the YAML frontmatter shapes; field order in the struct is rendering order. `Project`/`Issue` already use `yaml:"...,omitempty"`.
- `RunAmend` (`amend.go`) parses the note's existing frontmatter into a `doc`, and `renderAmendedFact`/`renderAmendedFeedback` (`amend.go:455-499`) re-render it, explicitly copying `Source`, `Project`, `Issue`, `Tier` from `doc` — never from fresh args or freshly-detected values. That preserve-verbatim path continues to apply to those four fields; `Repo`/`User`/`Vault` deliberately do not join it (see Decisions).
- No existing precedent for OS-username or `git config` reads anywhere in the codebase (verified: no `os/user`, `$USER`/`$LOGNAME`, `user.Current()`, or `git config` invocation exists today).
- `--vault`/`ENGRAM_VAULT_PATH` already resolves flag → env → default (`docs/GLOSSARY.md:18-19`); `--vault-name`/`ENGRAM_VAULT_NAME` mirrors that exact shape.
- `internal/cli/update.go`'s `runUpdate` (lines ~439-507) already runs a five-detector, notify-only detect-and-notify convention after a successful update (ADR-0021, `docs/architecture/adr.md:689-698`): `oldVocabFilesPresent`, `vocabDefinitionsMissingSelfTags`, `vaultHasOnlyTopLevelNotes`, `chunkIndexHasEmptyFiles`, `chunkIndexHasPrunableDuplicates`. Each flags a vault condition and points to the exact command that fixes it; each is explicitly notify-only — an earlier design that auto-ran a fix was deliberately reversed ("Reversed, 2026-07-26 (Joe, mid-cycle): detect-and-notify, not auto-run").
- `amend.go:171`'s `contentChanged` return value is already scoped to semantic fields only (situation/subject/predicate/object/behavior/impact/action); the doc comment explicitly names "Provenance-only or supersedes-only changes" as the category that does NOT set it (D3, `amend.go:247-249,269-271`) — identity re-stamping fits this existing category exactly.

## Goals / Non-Goals

**Goals:**
- Stamp `repo:`/`user:`/`vault:` on every note write, using only the injected-primitive DI pattern already established.
- Reuse `Getwd` and `Commander` rather than introducing a new kind of adapter seam.
- Re-stamp `repo`/`user`/`vault` fresh on every `learn` or `amend` call, using the same detection path in both places — these fields track the note's most recent writer, not its origin.
- Provide an opt-in backfill path (`engram update --backfill-identity`) for notes written before this capability existed, following the existing detect-and-notify convention (ADR-0021) rather than inventing a new mechanism.

**Non-Goals:**
- No credential verification, authentication, or server-side identity stamping — this change is entirely local/client-side detection (see proposal.md - "self-report for now" decision).
- No change to `query --project` filtering or any read-path behavior.
- No new vault-level metadata/config file — `vault-name` is a per-invocation resolved value (flag/env/default), not persisted at `engram vault init` time.

## Decisions

**Repo detection composes `Getwd` + `Commander`, not a new primitive kind.** `git remote get-url origin` and (for the no-origin fallback) `git rev-parse --show-toplevel` both run via the existing `Commander.Run(ctx, dir, "git", args...)` seam, with `dir` supplied by `deps.Getwd()`. Alternative considered: reading `.git/config` directly via `FS.ReadFile` to avoid a subprocess — rejected because it would need to reimplement git's own config-resolution precedence (worktrees, includeIf, etc.) for no real benefit; shelling out to `git` is what `update`'s Commander already does for exactly this class of problem.

**User detection reuses the same `Commander` seam for `git config user.email`; the OS-username fallback needs one new primitive.** `git config user.email` (run via `Commander`, no `dir` requirement — global config resolves independent of cwd) covers the primary path. Fallback to OS username needs a new `Primitives.Proc`-level function (mirroring the existing `Getwd`) — e.g. wrapping `os/user.Current()` in `cmd/engram`, composed the same way `Getwd: prims.Proc.Getwd` already is. This is new surface, but the same shape as everything else in `Primitives`.

**`vault:` resolution is a plain flag/env/default read, not detection.** No git or filesystem probe involved — it's the same `targ:"flag,name=...,env=..."` struct-tag mechanism `VaultPath` already uses on `QueryArgs`/other `*Args` structs, applied to a new `LearnArgs.VaultName string` field with default `"personal"` applied where the flag/env resolve to empty.

**Identity fields are re-stamped on every write, not preserved as origin metadata.** Reversed from the original v1 decision after review: `repo`/`user`/`vault` describe the *last writer*, matching `source:`'s existing precedent of describing current state rather than an immutable history. `amend` now calls the same detection functions `learn` uses, unconditionally, on every invocation — regardless of which (if any) content flags were passed. This is new production logic in `amend.go` (`applyFieldReplacement`/`applyTypedAmend`'s override step gains an unconditional identity re-stamp, alongside the existing supplied-value overrides), not a copy-forward. It composes cleanly with the existing re-embed gate: `contentChanged` is already scoped to semantic fields only and explicitly excludes provenance-only changes from triggering re-embed (D3, see Context) — identity re-stamping is exactly this category, so it never marks `contentChanged` and never forces a re-embed.

**Repo re-detection prefers the note's own `project:` field over a fresh git-remote read — for backfill only, not `amend`.** Backfill runs once, vault-wide, from a single working directory, and may touch notes whose `project:` reflects a different repo (a personal vault spanning multiple projects) — `project:` is per-note, human-supplied, and already trusted for `query --project` filtering, making it a better per-note signal than backfill's single invocation cwd. Falls back to fresh git detection only when `project:` is empty. `amend`'s repo re-stamp deliberately does *not* use this fallback: an amend is assumed to run from the repo it's actually about, so its `repo:` value should always reflect exactly where the amend was fired from, even when that differs from the note's original `project:` — that's a real, wanted signal (e.g. the note is being amended from a fork or a differently-named clone), not a case to paper over. Accepted trade-off: `repo:`'s range already includes a non-URL fallback (the no-origin basename case), so a `project:`-derived backfill value being a free-text slug rather than a URL doesn't introduce a new shape, just a new source for an already-heterogeneous field.

**Backfill is detector #6 in `engram update`'s existing detect-and-notify convention, not a new mechanism.** A `notesMissingIdentityFields` detector joins the five described in Context, its notice pointing to a new `--backfill-identity` flag on `engram update` (matching `--regen-vocab`/`--reparent-luhmann`'s existing flag-on-update shape rather than a new subcommand). Unlike the other five detectors, this one cannot fully reconstruct the original state — the note's actual creation-time repo/user/vault context is gone — so it stamps the current environment's identity (with the `project:`-preferred repo fallback above) as a best-effort value, indistinguishable in the frontmatter from a normally-stamped field. Explicitly accepted: this is the first `engram update` detector whose fix rewrites vault note content rather than chunk-index/vocab-file state.

**Missing-git-repo and missing-origin-remote resolve to `omitempty`/basename, not an error.** `RunLearn` must not fail just because the working directory isn't a git repo (e.g., a throwaway or non-git workspace) — matches `Project`'s existing `omitempty` precedent rather than introducing a new required-field failure mode.

## Risks / Trade-offs

- **[Self-reported identity is spoofable]** → Accepted for v1 per proposal.md; the frontmatter shape (separate `repo:`/`user:`/`vault:` fields rather than folding into `source:`) is chosen specifically so a later credential-verified resolution can replace the detection logic without a schema migration.
- **[`git config user.email` can be empty even inside a configured git install if only `user.name` is set]** → Falls back to OS username per the requirement; no error path needed.
- **[Shelling out to `git` twice per `learn` call (remote + config) adds process-spawn latency]** → Matches existing `update`'s Commander usage pattern; `learn` is not a hot/high-frequency path (unlike `query`), so the cost is acceptable without measurement.
- **[Two remotes named differently, or a non-`origin` primary remote]** → Out of scope; `origin` is the convention this design commits to, consistent with picking one deterministic signal rather than a remote-selection heuristic.
- **[Amending a note erases its origin provenance]** → Once any `amend` touches a note, its original creator's `repo`/`user`/`vault` are gone — overwritten by whoever ran the amend. Accepted: `source:` already has this same "current state, not history" character, and issue #720's future client/server identity model is the intended place to add verified, historical provenance if that's later needed.
- **[Backfilled identity can't recover true origin]** → A note's actual creation-time environment isn't recoverable; backfill necessarily stamps today's environment. Accepted per this change's shipping context (pre-#720, single-operator use, no cross-vault trust yet), with the `project:`-preferred repo fallback narrowing the blast radius of a wrong guess to just `repo`, and `user`/`vault` staying safe to blind-stamp as vault-wide constants.

## Migration Plan

No schema version bump, no flag removed, no automatic rewrite. `--vault-name`/`ENGRAM_VAULT_NAME` default to `"personal"` so no existing invocation's behavior changes without opting in. New: `engram update` detects notes missing `repo`/`user`/`vault` and surfaces a notify-only notice (matching the existing five-detector convention) pointing to `--backfill-identity`; existing notes are only rewritten when the user explicitly passes that flag — no note is touched without an explicit `amend` or `--backfill-identity` invocation. Once backfilled or amended, a note's identity fields reflect the environment of that write, not its original creation. No rollback concerns beyond a normal revert; `--backfill-identity` is idempotent (only touches notes currently missing all three fields).
