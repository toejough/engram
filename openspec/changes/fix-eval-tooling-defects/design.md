## Decisions

### #787 — audit instrument `--phrase`/`--text` flag parsing + error capture

**D1. Use `--phrase=<value>` form (equals-sign), not a positional-args refactor.** `_run_engram_query_at_moment` (`dev/eval/audit/audit_moments.py`) and the diagnostic rerun in `run_window_sample.py`'s `query_wrapper` both build `args = [..., "--phrase", phrase]`. Switching to `f"--phrase={phrase}"` (and `f"--text={text}"` wherever `--text` is built the same way) is a one-line change per call site that makes the value unparseable as a flag regardless of its content, verified directly: `engram query --lazy-chunks --phrase "--text foo bar"` reproduces `Error: flag needs an argument: --phrase` on stdout today; the `=` form does not. No alternative considered — this is the exact fix the issue specifies. **Mechanism, corrected (twice now — see below)**: `engram`'s CLI is built on `github.com/toejough/targ` (`cmd/engram/main.go` imports it directly), not Go's stdlib `flag` package — `targ`'s own parser (`internal/core/parse.go` in the `targ` module: `errFlagNeedsArgument = errors.New("flag needs an argument")` is the exact source of the observed error text) splits a `--name=value` argument via `strings.Index(name, "=")` (`parseFlagArgWithPosition`, `internal/core/parse.go:546-550`, and again at line 570 for the short-flag path) — **not** `strings.SplitN`, which was my own prior draft's mistake (there is a `strings.SplitN(value, "=", keyValueParts)` elsewhere in that file, at line 835, but it belongs to a different code path — parsing `KEY=VALUE` pairs for a map-typed flag like `--env`, not the `--phrase=value` single-value split this fix depends on). Either mechanism would produce the same observable result (`--flag=value` supported for every flag), so this correction doesn't change the fix itself — D1's `f"--phrase={phrase}"` construction and the direct verification against the real `engram` binary are unaffected — but the cited source line was wrong and is fixed here.

**D1 implementation note (Gate B round 2, blocking finding):** hand-mirroring the `f"--phrase={phrase}"` construction into both call sites separately is exactly how #787 came to exist in two places (the primary invocation and `run_window_sample.py`'s diagnostic rerun drifted apart once before). Implemented as a single shared `_build_engram_query_argv(search_phrases)` helper in `audit_moments.py` (returning `["engram", "query", "--lazy-chunks", *("--phrase=<value>" for each phrase)]`), with both `_run_engram_query_at_moment` and `run_window_sample.py`'s `query_wrapper` (which already imports `audit_moments`) calling it — so the two invocations can never diverge again. Covered by a direct unit test on the helper and a RED-verified test exercising `query_wrapper`'s diagnostic-rerun path through the real `_run_engram_query_at_moment` (not a stub), confirmed to fail against a reverted call site before the fix.

**D2. Capture both stdout and stderr on a non-zero exit, not stderr alone.** Verified: `engram`'s own CLI error goes to **stdout**, not stderr (`Error: flag needs an argument: --phrase` printed to stdout, stderr empty, confirmed by direct invocation). The current code's error path (`audit_moments.py::_run_engram_query_at_moment`) builds `error_msg = f"engram query failed with rc {result.returncode}: {result.stderr}"`, silently dropping the real text. Fix: include `result.stdout` in the message whenever it's non-empty (e.g. `f"...: stdout={result.stdout!r} stderr={result.stderr!r}"` or stdout-first since that's where `engram` actually writes), so a real failure's cause is always in the record. `run_window_sample.py`'s diagnostic reruns already capture both streams (`rerun_stdout_tail`/`rerun_stderr_tail`) for its own failure log — the only gap is the primary record's own `error` field, which is what feeds `memory_existed`.

**D3. Both new RED tests are mocked unit tests, matching the existing style for this exact function — not a new real-binary integration test.** Verified: `dev/eval/audit/test_audit_moments.py` already has a dedicated test class covering `_run_engram_query_at_moment` with `unittest.mock.patch("subprocess.run")` (`test_run_engram_query_subprocess_failure`, `test_run_engram_query_timeout`, `test_run_engram_query_success_no_results`, around line 1948) — there is a *separate*, real-vault integration test elsewhere in the same file (`test_live_vault_unchanged_after_ptc_check`), but it is host-dependent (`pytest.skip` if `~/.local/share/engram/vault` doesn't exist) and exists to prove the point-in-time check doesn't mutate the live vault, not to cover CLI-argument edge cases. Per this repo's CLAUDE.md test-categorization rule (unit tests verify business logic via DI + mocks; integration tests verify wiring of thin I/O wrappers with real dependencies; refactor rather than writing an integration test around a function that mixes both), the behavior under test here — "does our own code build the right argv, and does it preserve the right error text from a given subprocess result" — is pure non-I/O logic once `subprocess.run`'s inputs/outputs are the seam, so it belongs in the existing mocked class: (1) mock `subprocess.run`, call `_run_engram_query_at_moment` with a phrase starting with `--`, and assert the captured `call_args` show `--phrase=<value>` (a single joined argument, not two list elements) — this proves OUR code can no longer produce a mis-parseable invocation, without needing the real binary to prove `targ`'s parser accepts it (that's `targ`'s own contract, exercised directly in D1's verification, not re-tested here); (2) mock `subprocess.run` to return `returncode=1`, `stdout="Error: flag needs an argument: --phrase"`, `stderr=""`, and assert the returned `error` field contains that stdout text. No new real-binary integration test is added in this change.

**D3b. `extract.py:350`'s `re.finditer(r'--phrase\s+"([^"]+)"', command)` is unrelated to this fix and is left unchanged — resolved here, not left as an implementer's judgment call.** Verified: this regex parses `command` text found inside a `bash` tool-call block of a real transcript *under audit* (an agent being analyzed, not our own instrument) — it extracts the search phrases an audited agent's own `engram query` bash invocation used, as part of reconstructing that agent's recall calls for scoring. It has nothing to do with `_run_engram_query_at_moment`'s own invocation (D1/D2's fix target) — different data source entirely (historical transcripts of audited agents' bash commands vs. the audit instrument's own subprocess call). Audited agents commonly phrase recall calls with the space-separated `--phrase "value"` form (matching how `agent-instructions/skills/recall/SKILL.md` itself documents the invocation), so this extractor should keep matching that form going forward — D1's `=`-form fix is scoped to our instrument's own `engram query` construction only, and does not change what form audited agents use in the wild. No change to `extract.py`.

### #754 — history-rewrite steps.json regex

**D4. Broaden the pattern with a left word-boundary guard, not a bare character-class widening.** `git\s+(filter-branch|filter-repo)\b` → `(?<![\w-])git[\s-]+(filter-branch|filter-repo)\b`. **Correction**: the issue's suggested `git[\s-]+(filter-branch|filter-repo)\b` (and my first draft of it) is wrong — widening `\s+` to `[\s-]+` without also guarding `git`'s own left edge introduces a *new* false-positive class the original space-only pattern didn't have: `[\s-]` now treats `-` as an acceptable separator, so the bare substring `git-filter-repo` inside `digit-filter-repo` or `mygit-filter-repo` matches too (`digit` contains the literal substring `git`, immediately followed by `-filter-repo`). The negative-lookbehind `(?<![\w-])` requires that whatever precedes `git` is neither a word character nor a hyphen, which rejects both `digit-filter-repo` and `mygit-filter-repo` while still matching `git-filter-repo`/`git filter-repo` at a command's start or after whitespace/most punctuation. Only `filter-repo` ships a standalone hyphenated script (`git-filter-repo`, commonly installed via pip/brew onto PATH); `git-filter-branch` is not a real binary anyone invokes that way, so the `[\s-]` separator widening is still correct for both alternatives — the fix needed is the left boundary, not the separator class. Test target: a `test_history_rewrite_steps` (or equivalent) test exercising `evaluate_steps`/the regex directly against both command forms plus three negatives — a command that merely contains the substring `filter-repo` without being a real invocation (e.g. inside a comment or filename), and the two letter-adjacent false positives named above (`digit-filter-repo ...`, `mygit-filter-repo ...`) — confirm it's covered in `dev/eval/cumulative/runbook_vs_skill/phase2/test_probe_phase2.py` or add it there.

### #750 — real-vault fingerprint guard false positive

**D8. Replace whole-vault diffing with trial-side detection, matching Joe's selected option ("Trial-side detection (Recommended)": *"Stop diffing the whole real vault. Assert each trial ran with an isolated `ENGRAM_VAULT_PATH` and that no new real-vault note names a trial dir/session in its source. Catches real leaks; ignores orchestrator writes entirely."*) — implemented as a process-wide, lock-guarded registry inside `isolation.py` itself, not by threading trial envs through each caller.**

**Correction to the prior draft (B1): "trial envs are already available to isolation.py's 7 external callers" was false, and the proposed fix of threading them through was real, non-trivial work this design should not have hand-waved past.** Verified: all 7 callers (`dev/eval/traps/{reasoning_eval,run,qanchor_eval,brun}.py`, `dev/eval/cumulative/endorse_cue/probe.py`, `dev/eval/cumulative/{please_step7_probe/run_probe,please_step3_probe/run_probe}.py`) call `isolation.isolated_env(cfg, state, cwd=wd)` *inside* a per-trial `run_one`-style worker function that a `concurrent.futures.ThreadPoolExecutor` pool runs; the worker's return value is a scored result dict that drops the env entirely, and `__main__`'s own `try/finally` around `main()` never sees `main()`'s return value either. Making the trial env reach the `__main__` guard would mean plumbing it out of every worker, through every pool's `as_completed`/result-collection loop, into whatever `main()` returns, in 7 differently-shaped files — real, per-file work, not a one-line change.

**Fix: `isolation.py`'s own env-builders register themselves — no caller threads anything.** Add a module-level, `threading.Lock`-guarded list inside `isolation.py` (safe under the same `ThreadPoolExecutor` concurrency all 7 callers already use for the workers themselves). `isolated_env(cfg, trial_dir, cwd=None, base=None)` appends `trial_dir` to it immediately after `assert_isolated(env, cwd)` succeeds (i.e., only ever an already-proven-isolated entry is recorded — `assert_isolated` already raises before this point if the env is not isolated, so registration can never record a non-isolated trial). `engram_env(vault, chunks=None, base=None)` registers `vault` the same way, right after `assert_engram_isolated(env)` succeeds — needed because `audit_moments.py::_run_engram_query_at_moment` and other direct-CLI callers use `engram_env`, not `isolated_env`, and #750's fix should cover both of this module's isolation entry points, per Joe's "keep probe.py/probe_phase2.py consistent with the same mechanism" instruction extended to every caller of either builder. A new `isolation.assert_no_trial_leak(before, vault=None)` reads this registry directly — no arguments beyond what `assert_vault_unchanged(before, vault=None)` already took. This makes every one of the 7 external callers' fix a literal one-line swap at the existing `__main__` guard site: the `_vault_before = isolation.vault_fingerprint()` line is unchanged (so `test_vault_guard.py`'s `vault_fingerprint(` grep stays green with no edit — see task 4.x), and only the `finally:` line's function name changes from `assert_vault_unchanged` to `assert_no_trial_leak`.

**D9b. Fingerprint format contract changes, not just the function name (R3).** `probe.py`'s `_real_vault_fingerprint` returns `(len(os.listdir(vault)), max(mtimes))` — a count of **every file** in the vault dir (including `.vec.json` sidecars) plus the newest **mtime** (a float). `isolation.vault_fingerprint` returns `(len(_note_names(vault)), sha256-of-sorted-basenames)` — a count of **only `.md` files**, plus a **content-independent basename hash** (no mtime anywhere). **D10. The guard still fails loud on a genuine leak — and this design states its limitations honestly, rather than claiming an equivalent-or-better detection ceiling to the old guard.** The mechanism is a single layer, not two: a new note appearing in the real vault after a run is flagged as a leak *only if* its content names one of the trial markers (`trial_dir` or `vault` path) recorded in the registry during that run; a new note that matches no registered marker is treated as an orchestrator-side write and does not raise. **Limitations, stated plainly (per the requesting feedback that the spec be honest about this), in four parts:**
1. A leak through any code path that never calls `isolated_env`/`engram_env` at all (bypassing this module's isolation contract entirely) is not caught by the registry.
2. A genuine leak whose resulting note content happens not to mention any registered trial marker is also not caught.

4. **(Gate-B follow-up, F2 + F2 round 2) The basename-fallback match is restricted to DISTINCTIVE basenames, which narrows limitation #2 slightly, in exchange for fixing a real over-detection bug.** `_is_distinctive_basename(basename)` requires the basename's trailing **`-`-delimited** segment to be at least 8 characters (the length of `tempfile.mkdtemp`'s default random suffix) — a marker's FULL path always counts, regardless of this check. **Split on `-` only, never `_` — confirmed by measurement, not assumption.** `tempfile`'s own random-name alphabet is `string.ascii_lowercase + string.digits + "_"` (it includes underscore), so an earlier draft that split on `[-_]` could cut a real mkdtemp suffix short at an embedded `_` (e.g. `"...-2vl_5xn_"` → a trailing empty-string segment after the last `_`) — measured at 987/5000 (and separately 91/500) realistic `sometrap-0-state-<suffix>` names misclassified as non-distinctive, silently disabling the basename fallback for roughly 1 in 5 trials at every mkdtemp-based call site. Splitting on `-` alone was verified 5000/5000 correct against real `tempfile.mkdtemp` output, and this harness's own deterministic trial-dir basenames — `probe.py`/`probe_phase2.py`'s `"plumbing-0"`, `"setup-only-0"`, `"history-rewrite-R-0"`, and the shorter `"R-0"`/`"F-3"` shapes — contain no `_` at all, so they classify correctly either way; the `_`-exclusion only changes the mkdtemp-suffix outcome, never this harness's own deterministic names. Without the basename-distinctiveness check at all, those same deterministic basenames false-matched an unrelated orchestrator note that merely mentioned the fixture by name in passing — a genuine new false-positive class, not a narrower version of an old one. The cost: a genuine leak whose note content names only a non-distinctive basename (never the full path, and never a sufficiently random-looking tail) is now also not caught — accepted, because the full-path match already covers the dominant real leak shape (a note quoting the exact trial path it was written from), and a short deterministic basename alone is exactly the signal too weak to trust either way.

These four limitations are also recorded in `specs/eval-trial-vault-leak-detection/spec.md`'s requirement text directly (not only here), per the requesting feedback.
