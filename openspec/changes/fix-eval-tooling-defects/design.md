## Context

Five independent `dev/eval` Python tooling defects, found during real audit/probe runs (#787, #754, #749, #750, #755), tracked together in `docs/ROADMAP.md` as one "eval-instrument defects batch." All five are measurement-validity bugs: each one silently produces a wrong or uninformative scoring/config/guard result rather than failing loud. This change proposes the fix for all five; **no implementation happens in this change** (per the requesting instruction) — `tasks.md` lays out the TDD (RED/GREEN/REFACTOR) steps for `/opsx:apply` to execute later.

Every fix here is Python, under `dev/eval/`. #710 tracks a future Go port of this tooling; whatever tests this change adds for each fix are the behavioral contract that port must preserve (see Risks).

Test invocation, verified (not assumed): `python3 -m pytest <specific file or dir> -v`, run from the repo root (`dev/eval/audit/HAND_VERIFICATION.md:140` confirms this pattern against a real file). **`pytest dev/eval/` as a whole-tree run is NOT used for verification in this change** — it has a confirmed pre-existing, unrelated bug (`dev/eval/LEDGER.md`'s #708 row): four duplicate module basenames across `dev/eval` subdirectories make a bare `pytest dev/eval/` import the wrong `score` module and fail 23 assertions in `recency_value/test_score.py`, independent of anything in this change. ## Decisions

### #787 — audit instrument `--phrase`/`--text` flag parsing + error capture

**D1. Use `--phrase=<value>` form (equals-sign), not a positional-args refactor.** `_run_engram_query_at_moment` (`dev/eval/audit/audit_moments.py`) and the diagnostic rerun in `run_window_sample.py`'s `query_wrapper` both build `args = [..., "--phrase", phrase]`. Switching to `f"--phrase={phrase}"` (and `f"--text={text}"` wherever `--text` is built the same way) is a one-line change per call site that makes the value unparseable as a flag regardless of its content, verified directly: `engram query --lazy-chunks --phrase "--text foo bar"` reproduces `Error: flag needs an argument: --phrase` on stdout today; the `=` form does not. No alternative considered — this is the exact fix the issue specifies. **Mechanism, corrected**: `engram`'s CLI is built on `github.com/toejough/targ` (`cmd/engram/main.go` imports it directly), not Go's stdlib `flag` package — `targ`'s own parser (`internal/core/parse.go` in the `targ` module: `errFlagNeedsArgument = errors.New("flag needs an argument")` is the exact source of the observed error text) splits a flag's value on `=` via `strings.SplitN(value, "=", 2)`, so `--flag=value` is supported for every flag the same way Go's stdlib `flag` package would support it — the fix mechanism is the same shape, the parser providing it is targ's, not Go's stdlib.

**D2. Capture both stdout and stderr on a non-zero exit, not stderr alone.** Verified: `engram`'s own CLI error goes to **stdout**, not stderr (`Error: flag needs an argument: --phrase` printed to stdout, stderr empty, confirmed by direct invocation). The current code's error path (`audit_moments.py::_run_engram_query_at_moment`) builds `error_msg = f"engram query failed with rc {result.returncode}: {result.stderr}"`, silently dropping the real text. Fix: include `result.stdout` in the message whenever it's non-empty (e.g. `f"...: stdout={result.stdout!r} stderr={result.stderr!r}"` or stdout-first since that's where `engram` actually writes), so a real failure's cause is always in the record. `run_window_sample.py`'s diagnostic reruns already capture both streams (`rerun_stdout_tail`/`rerun_stderr_tail`) for its own failure log — the only gap is the primary record's own `error` field, which is what feeds `memory_existed`.

**D3. Both new RED tests are mocked unit tests, matching the existing style for this exact function — not a new real-binary integration test.** Verified: `dev/eval/audit/test_audit_moments.py` already has a dedicated test class covering `_run_engram_query_at_moment` with `unittest.mock.patch("subprocess.run")` (`test_run_engram_query_subprocess_failure`, `test_run_engram_query_timeout`, `test_run_engram_query_success_no_results`, around line 1948) — there is a *separate*, real-vault integration test elsewhere in the same file (`test_live_vault_unchanged_after_ptc_check`), but it is host-dependent (`pytest.skip` if `~/.local/share/engram/vault` doesn't exist) and exists to prove the point-in-time check doesn't mutate the live vault, not to cover CLI-argument edge cases. Per this repo's CLAUDE.md test-categorization rule (unit tests verify business logic via DI + mocks; integration tests verify wiring of thin I/O wrappers with real dependencies; refactor rather than writing an integration test around a function that mixes both), the behavior under test here — "does our own code build the right argv, and does it preserve the right error text from a given subprocess result" — is pure non-I/O logic once `subprocess.run`'s inputs/outputs are the seam, so it belongs in the existing mocked class: (1) mock `subprocess.run`, call `_run_engram_query_at_moment` with a phrase starting with `--`, and assert the captured `call_args` show `--phrase=<value>` (a single joined argument, not two list elements) — this proves OUR code can no longer produce a mis-parseable invocation, without needing the real binary to prove `targ`'s parser accepts it (that's `targ`'s own contract, exercised directly in D1's verification, not re-tested here); (2) mock `subprocess.run` to return `returncode=1`, `stdout="Error: flag needs an argument: --phrase"`, `stderr=""`, and assert the returned `error` field contains that stdout text. No new real-binary integration test is added in this change.

**D3b. `extract.py:350`'s `re.finditer(r'--phrase\s+"([^"]+)"', command)` is unrelated to this fix and is left unchanged — resolved here, not left as an implementer's judgment call.** Verified: this regex parses `command` text found inside a `bash` tool-call block of a real transcript *under audit* (an agent being analyzed, not our own instrument) — it extracts the search phrases an audited agent's own `engram query` bash invocation used, as part of reconstructing that agent's recall calls for scoring. It has nothing to do with `_run_engram_query_at_moment`'s own invocation (D1/D2's fix target) — different data source entirely (historical transcripts of audited agents' bash commands vs. the audit instrument's own subprocess call). Audited agents commonly phrase recall calls with the space-separated `--phrase "value"` form (matching how `agent-instructions/skills/recall/SKILL.md` itself documents the invocation), so this extractor should keep matching that form going forward — D1's `=`-form fix is scoped to our instrument's own `engram query` construction only, and does not change what form audited agents use in the wild. No change to `extract.py`.

### #754 — history-rewrite steps.json regex

**D4. Broaden the pattern with a left word-boundary guard, not a bare character-class widening.** `git\s+(filter-branch|filter-repo)\b` → `(?<![\w-])git[\s-]+(filter-branch|filter-repo)\b`. **Correction**: the issue's suggested `git[\s-]+(filter-branch|filter-repo)\b` (and my first draft of it) is wrong — widening `\s+` to `[\s-]+` without also guarding `git`'s own left edge introduces a *new* false-positive class the original space-only pattern didn't have: `[\s-]` now treats `-` as an acceptable separator, so the bare substring `git-filter-repo` inside `digit-filter-repo` or `mygit-filter-repo` matches too (`digit` contains the literal substring `git`, immediately followed by `-filter-repo`). The negative-lookbehind `(?<![\w-])` requires that whatever precedes `git` is neither a word character nor a hyphen, which rejects both `digit-filter-repo` and `mygit-filter-repo` while still matching `git-filter-repo`/`git filter-repo` at a command's start or after whitespace/most punctuation. Only `filter-repo` ships a standalone hyphenated script (`git-filter-repo`, commonly installed via pip/brew onto PATH); `git-filter-branch` is not a real binary anyone invokes that way, so the `[\s-]` separator widening is still correct for both alternatives — the fix needed is the left boundary, not the separator class. Test target: a `test_history_rewrite_steps` (or equivalent) test exercising `evaluate_steps`/the regex directly against both command forms plus three negatives — a command that merely contains the substring `filter-repo` without being a real invocation (e.g. inside a comment or filename), and the two letter-adjacent false positives named above (`digit-filter-repo ...`, `mygit-filter-repo ...`) — confirm it's covered in `dev/eval/cumulative/runbook_vs_skill/phase2/test_probe_phase2.py` or add it there.

### #749 — matrix.py build_cfg_template warm-skills path

**D5. Mirror `wrun.py::build_warm_cfg`'s exact pattern (verified fixed under the existing `eval-warm-config-fidelity` spec), not a new design.** `dev/eval/traps/wrun.py:26-43` already implements the corrected contract: source path `agent-instructions/skills/<skill>` (not hardcoded, derived from `REPO`), raise on missing source dir, raise on missing `SKILL.md`, raise if the post-copy destination doesn't actually have `SKILL.md`. Apply the identical pattern to `matrix.py::build_cfg_template`'s `warm` branch (lines 84-89 today). `matrix.py`'s own `REPO` constant (line 26: `os.path.dirname(os.path.dirname(os.path.dirname(CUM)))`) already resolves correctly from `__file__` — only the subpath (`"skills"` → `"agent-instructions", "skills"`) and the raise-on-missing behavior change.

**D6. Do NOT make `probe.py::build_cfg_template` delegate to the fixed `matrix.py::build_cfg_template` — not DRY-able without a behavior change.** Verified: `probe.py`'s version (`dev/eval/cumulative/runbook_vs_skill/probe.py:143-176`) takes a `skills: tuple` parameter (default `("recall", "learn")`, callable with `skills=()` for the shim-only/no-skills trial arms the `runbook-shim-follow-frame` change added) — `matrix.py::build_cfg_template` takes a `warm: bool` that unconditionally installs exactly `("recall", "learn")`. Decision: keep `probe.py`'s local copy, but (i) apply the same raise-on-missing-source behavior to it for consistency (it currently still silently skips via `if os.path.isdir(src):` with no raise — not itself one of the five filed issues, but a one-line consistency fix while touching the function, since leaving it half-fixed invites the exact same silent-no-op bug class #749 just found), and (ii) update its docstring, which currently says "this is a corrected LOCAL copy" implying `matrix.py` is still broken — once `matrix.py` is fixed, the docstring's justification changes from "matrix.py is broken" to "matrix.py's signature doesn't support an empty skill set."

**D7. Enumerate affected result files — read-only, no re-runs, matches the issue's own instruction.** Grep every call site of `matrix.build_cfg_template(..., warm=True)` across `dev/eval/cumulative/` (found: `make_pools`, `underload_repro/run_underload_repro.py:210`, `run_recheck.py:584`), then for each, check whether any *committed* result artifact under its results directory predates or postdates the 2026-07-24 skills move (commit `a0b1ba92`, #697) — found by `git log`, not by the issue's own guessed "~2026-08-23" date (a discrepancy worth recording: the real move date is a month earlier). This is a `tasks.md` task producing a finding recorded in this file (see below), not a code change.

### #750 — real-vault fingerprint guard false positive

**D8. Replace whole-vault diffing with trial-side detection, matching Joe's selected option ("Trial-side detection (Recommended)": *"Stop diffing the whole real vault. Assert each trial ran with an isolated `ENGRAM_VAULT_PATH` and that no new real-vault note names a trial dir/session in its source. Catches real leaks; ignores orchestrator writes entirely."*) — implemented as a process-wide, lock-guarded registry inside `isolation.py` itself, not by threading trial envs through each caller.**

**Correction to the prior draft (B1): "trial envs are already available to isolation.py's 7 external callers" was false, and the proposed fix of threading them through was real, non-trivial work this design should not have hand-waved past.** Verified: all 7 callers (`dev/eval/traps/{reasoning_eval,run,qanchor_eval,brun}.py`, `dev/eval/cumulative/endorse_cue/probe.py`, `dev/eval/cumulative/{please_step7_probe/run_probe,please_step3_probe/run_probe}.py`) call `isolation.isolated_env(cfg, state, cwd=wd)` *inside* a per-trial `run_one`-style worker function that a `concurrent.futures.ThreadPoolExecutor` pool runs; the worker's return value is a scored result dict that drops the env entirely, and `__main__`'s own `try/finally` around `main()` never sees `main()`'s return value either. Making the trial env reach the `__main__` guard would mean plumbing it out of every worker, through every pool's `as_completed`/result-collection loop, into whatever `main()` returns, in 7 differently-shaped files — real, per-file work, not a one-line change.

**Fix: `isolation.py`'s own env-builders register themselves — no caller threads anything.** Add a module-level, `threading.Lock`-guarded list inside `isolation.py` (safe under the same `ThreadPoolExecutor` concurrency all 7 callers already use for the workers themselves). `isolated_env(cfg, trial_dir, cwd=None, base=None)` appends `trial_dir` to it immediately after `assert_isolated(env, cwd)` succeeds (i.e., only ever an already-proven-isolated entry is recorded — `assert_isolated` already raises before this point if the env is not isolated, so registration can never record a non-isolated trial). `engram_env(vault, chunks=None, base=None)` registers `vault` the same way, right after `assert_engram_isolated(env)` succeeds — needed because `audit_moments.py::_run_engram_query_at_moment` and other direct-CLI callers use `engram_env`, not `isolated_env`, and #750's fix should cover both of this module's isolation entry points, per Joe's "keep probe.py/probe_phase2.py consistent with the same mechanism" instruction extended to every caller of either builder. A new `isolation.assert_no_trial_leak(before, vault=None)` reads this registry directly — no arguments beyond what `assert_vault_unchanged(before, vault=None)` already took. This makes every one of the 7 external callers' fix a literal one-line swap at the existing `__main__` guard site: the `_vault_before = isolation.vault_fingerprint()` line is unchanged (so `test_vault_guard.py`'s `vault_fingerprint(` grep stays green with no edit — see task 4.x), and only the `finally:` line's function name changes from `assert_vault_unchanged` to `assert_no_trial_leak`.

**D9. Caller-by-caller disposition** (full enumeration — the decision to migrate every caller, not just `probe.py`, is this design's own call, reasoned below; Joe selected the trial-side-detection *approach*, not a per-caller list):
- `dev/eval/cumulative/runbook_vs_skill/probe.py` (`_real_vault_fingerprint`, 2 call sites: `run_batch`'s pooled-trial run at line 746, `run_plumbing` at line 795 — not `main`, which only parses args and dispatches to `run_batch`/`run_plumbing`) — **fix**: this is the call site that actually demonstrated the false positive (vault note 956). Since `probe.py` builds every trial's env via `trial_env`, which itself calls `isolation.isolated_env(...)` internally, the registry change above covers it automatically once `_real_vault_fingerprint`'s print-based `ABORT-REPORT` is replaced with a call into `isolation.assert_no_trial_leak`, caught locally and reported the same way (`probe.py` currently prints a non-raising `ABORT-REPORT` to stderr inside a `finally` before its own `shutil.rmtree` cleanup; preserve that non-raising-to-the-caller posture by catching `isolation.IsolationError` and printing it, rather than letting it propagate and skip the cleanup).
- `dev/eval/cumulative/runbook_vs_skill/phase2/probe_phase2.py` (imports `p1._real_vault_fingerprint`, 4 call sites across its own trial-running functions) — **fix**: same change, inherited automatically once `probe.py`'s function is migrated to call `isolation.assert_no_trial_leak` (it's imported, not copied).
- `dev/eval/isolation.py::vault_fingerprint`/`assert_vault_unchanged`, used as an end-of-run `__main__` bracket by the 7 harnesses named above — **fix the shared primitive once**, and migrate every one of the 7 callers' `finally:` line (not 6, not "the risky ones") rather than leaving some on the old whole-vault-diff guard. Reasoning for migrating all 7, in this design's own voice, not Joe's: (a) they share the exact same false-positive class as `probe.py`'s demonstrated case — any of the 7 is run from an interactive session that also touches the real vault (a `/route` glance, a `/recall`, a manual `engram learn` in another terminal) during a long batch run, and would false-alarm identically; the fact that none has *yet* demonstrated it is not evidence the class doesn't apply, only that nobody has hit it yet. (b) Leaving these 7 on the old guard while `probe.py`/`probe_phase2.py` move to the new one means two divergently-shaped vault-leak guards coexist in the same codebase indefinitely, doubling the surface `test_vault_guard.py` (and any future maintainer) has to reason about for no retained benefit. (c) `test_vault_guard.py` already asserts, structurally, that "every harness in `HARNESSES` calls `assert_vault_unchanged(`" — once that assertion is updated to the new call name (task 4.x, per B2), uniform migration is what keeps that single structural test meaningful; a mixed fleet would need the test itself to special-case which harnesses use which guard, which is strictly worse than migrating all 7.

**D10. The guard still fails loud on a genuine leak — and this design states its limitation honestly, rather than claiming an equivalent-or-better detection ceiling to the old guard.** The mechanism is a single layer, not two: a new note appearing in the real vault after a run is flagged as a leak *only if* its content names one of the trial markers (`trial_dir` or `vault` path) recorded in the registry during that run; a new note that matches no registered marker is treated as an orchestrator-side write and does not raise. **Limitation, stated plainly (per the requesting feedback that the spec be honest about this): a leak through any code path that never calls `isolated_env`/`engram_env` at all (bypassing this module's isolation contract entirely) is not caught by the registry, and a genuine leak whose resulting note content happens not to mention any registered trial marker is also not caught.** This is the same class of blind spot the *old* whole-vault-diff guard also could not close on its own (its own docstring already frames it as "the backstop for a path the env vars do not cover," never a complete guarantee) — the new guard does not regress coverage of a *mediated* leak (one that went through `isolated_env`/`engram_env`, which is how every known call site in `dev/eval` spawns `engram`/`claude -p` today) and removes the false-positive class that cost an investigation in #750, but it is not, and is not claimed to be, an unconditional leak-proof. This limitation is also recorded in `specs/eval-trial-vault-leak-detection/spec.md`'s requirement text directly (not only here), per the requesting feedback.

### #755 — question_stop order-awareness + bisect-before-fix fixture

**D11. Thread the already-computed `end_state` boolean into `detect_question_stop`, short-circuiting to `False` when it's `True` — no new transcript-position tracking needed.** Verified: if a trial's final on-disk state already satisfies `done_when_checks.sh` (`end_state=True`), then by construction every mutation the task required already happened — and `detect_question_stop`'s existing scan already proves no mutation follows the last ambiguity-posing text. Combining these two facts: if `end_state` is `True` and no mutation follows the last ambiguity, that ambiguity cannot have blocked any required mutation — it is necessarily a trailing, already-irrelevant remark. So `question_stop` SHALL be `False` whenever `end_state` is `True`, full stop; no separate "did completion precede the ambiguity" position-tracking logic is needed, because `end_state=True` already proves it. Both call sites (`probe_phase2.py:1588` in `score_fields`, and `:2465` in the rescore path) need `end_state` computed *before* calling `detect_question_stop` — today the first call site computes `end_state` (line 1594) *after* `question_stop` (line 1588); reorder so `end_state` is available first, matching the second call site's existing order (there, `end_state` at line 2456 is already before `detect_question_stop` at line 2465, so only the first call site needs reordering). `detect_question_stop`'s signature becomes `detect_question_stop(events, task_key, end_state)` — a required third argument, not a default, so a future call site can't silently skip wiring it and regress to the current bug.

**D12. The `bisect-before-fix` fixture gets an `ISSUES.md` baked into the template directory (present from the initial commit), named in `task-prompt.txt`.** `dev/eval/cumulative/runbook_vs_skill/phase2/fixtures/fixture-repo-templates/bisect-before-fix-task/` is `cp -r`'d wholesale by `init_fixture_repo.sh` before the first commit, so adding `ISSUES.md` there makes it present at both the parent commit and final HEAD automatically — no init-script change needed. `task-prompt.txt` gains one sentence naming it as the place to file a follow-up issue, giving the runbook's step 6 ("file the pre-existing regression as its own separate issue") an actual local target to act on.

**D13. `done_when_checks.sh` is NOT updated to require an `ISSUES.md` entry; `steps.json` gets a new tracked (not pass/fail-gating) step instead.** `done_when_checks.sh` measures the fixture's core-task correctness (gate passes, `bar.py` fixed) **uniformly across all four arms** (R/F/S/N) for the harness's own cross-arm comparison — but only the runbook (arm R, when shim-following) is ever told about runbook 846's own `done_when` text requiring a filed issue. Making `done_when_checks.sh` fail on a missing `ISSUES.md` entry would fail arms that were never instructed to file one, corrupting the very cross-arm `end_state` comparison this harness exists to produce. Instead, add a `steps.json` step (e.g. step 8, gated `"after": 6`) detecting an `ISSUES.md` edit (`tool_path` on `ISSUES\.md$`, or a `bash_regex` for an append), scored into `followed_steps`/`followed_all` (which are already per-arm-relative, not a uniform pass/fail bar) — this answers "did a runbook-following trial actually comply with step 6" without biasing `end_state`.

## Risks / Trade-offs

- **[Risk] #710's future Go port inherits whatever test coverage these fixes get — thin coverage here becomes a silent gap there.** → Mitigation: every task below names a specific behavioral test — a real regex match, a real fixture state, a real registry under real thread concurrency, or (for #787, per D3) a mocked assertion on the exact argv/error-text contract `_run_engram_query_at_moment` must uphold — so the port has a concrete contract to satisfy either way; noted again in `tasks.md`'s own framing. #787 is the one deliberate exception to "real invocation": its mocked tests assert OUR OWN argv-construction and error-capture logic, not `targ`'s parser (which is a separate, already-verified fact in D1, not something this change's tests need to re-prove).
- **[Risk] The module-level trial-marker registry (D8) is written to concurrently by `ThreadPoolExecutor` worker threads across 9 call sites, and is new global state in a module that was previously stateless.** → Mitigation: guarded by a single `threading.Lock` around every append and every read; the registry is append-only for the duration of one process's run (no removal), so there is no read/write ordering hazard beyond the lock itself; `dev/eval/test_isolation.py` gets a concurrency-shaped test (multiple threads calling `isolated_env` simultaneously, then asserting the registry contains all of them) rather than trusting the lock by inspection alone.
- **[Risk] `isolation.py` touches 9 call sites outside the two issues' own "Affected files" lists (7 `assert_vault_unchanged` callers + `probe.py` + `probe_phase2.py`), even though each is now only a one-line swap.** → Mitigation: `tasks.md` gives each of the 7 external callers its own explicit sub-task (B5: one file per sub-task, not one task covering all 7), so a mistake in one doesn't block or get hidden among the others; the old `vault_fingerprint`/`assert_vault_unchanged` functions are kept in `isolation.py` rather than deleted (callers simply stop invoking `assert_vault_unchanged`), minimizing the diff's blast radius and leaving a trivial revert path per file.
- **[Risk] D6's extra raise-on-missing-source fix to `probe.py` is not itself one of the five filed issues.** → Mitigation: flagged explicitly here and in `tasks.md` as a small, scoped, same-root-cause fix made while already touching the function for the docstring update — not separate scope creep, and reported as a decision rather than silently bundled.
- **[Trade-off] D11 makes `end_state` a required argument to `detect_question_stop`, a breaking signature change for any caller outside the two known ones.** → Mitigation: grepped — confirmed exactly two call sites exist in the whole repo; both are updated by this change.

## Migration Plan
