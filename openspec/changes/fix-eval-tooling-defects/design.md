## Context

Five independent `dev/eval` Python tooling defects, found during real audit/probe runs (#787, #754, #749, #750, #755), tracked together in `docs/ROADMAP.md` as one "eval-instrument defects batch." All five are measurement-validity bugs: each one silently produces a wrong or uninformative scoring/config/guard result rather than failing loud. This change proposes the fix for all five; **no implementation happens in this change** (per the requesting instruction) — `tasks.md` lays out the TDD (RED/GREEN/REFACTOR) steps for `/opsx:apply` to execute later.

Every fix here is Python, under `dev/eval/`. #710 tracks a future Go port of this tooling; whatever tests this change adds for each fix are the behavioral contract that port must preserve (see Risks).

Test invocation, verified (not assumed): `python3 -m pytest <specific file or dir> -v`, run from the repo root (`dev/eval/audit/HAND_VERIFICATION.md:140` confirms this pattern against a real file). **`pytest dev/eval/` as a whole-tree run is NOT used for verification in this change** — it has a confirmed pre-existing, unrelated bug (`dev/eval/LEDGER.md`'s #708 row): four duplicate module basenames across `dev/eval` subdirectories make a bare `pytest dev/eval/` import the wrong `score` module and fail 23 assertions in `recency_value/test_score.py`, independent of anything in this change. ## Decisions

### #787 — audit instrument `--phrase`/`--text` flag parsing + error capture

**D1. Use `--phrase=<value>` form (equals-sign), not a positional-args refactor.** `_run_engram_query_at_moment` (`dev/eval/audit/audit_moments.py`) and the diagnostic rerun in `run_window_sample.py`'s `query_wrapper` both build `args = [..., "--phrase", phrase]`. Switching to `f"--phrase={phrase}"` (and `f"--text={text}"` wherever `--text` is built the same way) is a one-line change per call site that makes the value unparseable as a flag regardless of its content, verified directly: `engram query --lazy-chunks --phrase "--text foo bar"` reproduces `Error: flag needs an argument: --phrase` on stdout today; the `=` form does not. No alternative considered — this is the exact fix the issue specifies and Go's `flag` package (which `engram`'s CLI is built on) supports `--flag=value` for every flag.

**D2. Capture both stdout and stderr on a non-zero exit, not stderr alone.** Verified: `engram`'s own CLI error goes to **stdout**, not stderr (`Error: flag needs an argument: --phrase` printed to stdout, stderr empty, confirmed by direct invocation). The current code's error path (`audit_moments.py::_run_engram_query_at_moment`) builds `error_msg = f"engram query failed with rc {result.returncode}: {result.stderr}"`, silently dropping the real text. Fix: include `result.stdout` in the message whenever it's non-empty (e.g. `f"...: stdout={result.stdout!r} stderr={result.stderr!r}"` or stdout-first since that's where `engram` actually writes), so a real failure's cause is always in the record. `run_window_sample.py`'s diagnostic reruns already capture both streams (`rerun_stdout_tail`/`rerun_stderr_tail`) for its own failure log — the only gap is the primary record's own `error` field, which is what feeds `memory_existed`.

**D3. Regression test exercises the real CLI, not a mock.** Per this repo's own test-categorization convention (unit = DI+mocks, integration = real wiring), this is a thin I/O wrapper around a real subprocess — the existing test file already runs real `engram` binary invocations under isolation (verify at implementation time); the regression test adds one case with a leading-`--` phrase and asserts `items`/`error` reflect success, not a flag-parse failure.

### #754 — history-rewrite steps.json regex

**D4. Broaden the pattern in place; no new signal type needed.** `git\s+(filter-branch|filter-repo)\b` → `git[\s-]+(filter-branch|filter-repo)\b`, exactly as the issue specifies. Verified: only `filter-repo` ships a standalone hyphenated script (`git-filter-repo`, commonly installed via pip/brew onto PATH); `git-filter-branch` is not a real binary anyone invokes that way, so broadening the character class to `[\s-]` for *both* alternatives introduces no new false-positive class. Test target: a `test_history_rewrite_steps` (or equivalent) test exercising `evaluate_steps`/the regex directly against both command forms plus a negative (a command that merely contains the substring `filter-repo` without being a real invocation, e.g. inside a comment or filename) — confirm it's covered in `dev/eval/cumulative/runbook_vs_skill/phase2/test_probe_phase2.py` or add it there.

### #749 — matrix.py build_cfg_template warm-skills path

**D5. Mirror `wrun.py::build_warm_cfg`'s exact pattern (verified fixed under the existing `eval-warm-config-fidelity` spec), not a new design.** `dev/eval/traps/wrun.py:26-43` already implements the corrected contract: source path `agent-instructions/skills/<skill>` (not hardcoded, derived from `REPO`), raise on missing source dir, raise on missing `SKILL.md`, raise if the post-copy destination doesn't actually have `SKILL.md`. Apply the identical pattern to `matrix.py::build_cfg_template`'s `warm` branch (lines 84-89 today). `matrix.py`'s own `REPO` constant (line 26: `os.path.dirname(os.path.dirname(os.path.dirname(CUM)))`) already resolves correctly from `__file__` — only the subpath (`"skills"` → `"agent-instructions", "skills"`) and the raise-on-missing behavior change.

**D6. Do NOT make `probe.py::build_cfg_template` delegate to the fixed `matrix.py::build_cfg_template` — not DRY-able without a behavior change.** Verified: `probe.py`'s version (`dev/eval/cumulative/runbook_vs_skill/probe.py:143-170`) takes a `skills: tuple` parameter (default `("recall", "learn")`, callable with `skills=()` for the shim-only/no-skills trial arms the `runbook-shim-follow-frame` change added) — `matrix.py::build_cfg_template` takes a `warm: bool` that unconditionally installs exactly `("recall", "learn")`. Making `probe.py` delegate to `matrix.py` would require either (a) changing `matrix.py`'s signature to accept a `skills` tuple too — scope creep beyond #749's "fix the path, raise on missing" ask, and a behavior change to a function four other call sites depend on (`make_pools`, `underload_repro/run_underload_repro.py`, `run_recheck.py`) — or (b) losing the empty-skills-tuple capability `probe.py` needs. Decision: keep `probe.py`'s local copy, but (i) apply the same raise-on-missing-source behavior to it for consistency (it currently still silently skips via `if os.path.isdir(src):` with no raise — not itself one of the five filed issues, but a one-line consistency fix while touching the function, since leaving it half-fixed invites the exact same silent-no-op bug class #749 just found), and (ii) update its docstring, which currently says "this is a corrected LOCAL copy" implying `matrix.py` is still broken — once `matrix.py` is fixed, the docstring's justification changes from "matrix.py is broken" to "matrix.py's signature doesn't support an empty skill set."

**D7. Enumerate affected result files — read-only, no re-runs, matches the issue's own instruction.** Grep every call site of `matrix.build_cfg_template(..., warm=True)` across `dev/eval/cumulative/` (found: `make_pools`, `underload_repro/run_underload_repro.py:210`, `run_recheck.py:584`), then for each, check whether any *committed* result artifact under its results directory predates or postdates the 2026-07-24 skills move (commit `a0b1ba92`, #697) — found by `git log`, not by the issue's own guessed "~2026-08-23" date (a discrepancy worth recording: the real move date is a month earlier). This is a `tasks.md` task producing a finding recorded in this file (see below), not a code change.

### #750 — real-vault fingerprint guard false positive

**D8. Replace whole-vault diffing with trial-side detection, per Joe's decision — implemented as a new shared helper in `isolation.py`, called by both guard implementations.** Rationale for centralizing rather than fixing `probe.py::_real_vault_fingerprint` and `isolation.py::vault_fingerprint`/`assert_vault_unchanged` independently: both exist to answer the same question ("did a trial, not the orchestrator, reach the real vault") and the fix is identical in shape for both — assert each completed trial's recorded isolation evidence, then scope any remaining real-vault content scan to notes naming a trial dir/session id. A single `isolation.py` primitive (e.g. `assert_no_trial_leak(trial_envs, vault=None)`) keeps the two implementations from drifting again.

**D9. Caller-by-caller disposition** (full enumeration, per the issue's explicit ask):
- `dev/eval/cumulative/runbook_vs_skill/probe.py` (`_real_vault_fingerprint`, 2 call sites: `main`'s pooled-trial run, `run_plumbing`) — **fix**: this is the call site that actually demonstrated the false positive (vault note 956); replace with trial-side detection. `probe.py` already threads per-trial envs through `trial_env`/`run_one_trial`, so the trial-side evidence (`ENGRAM_VAULT_PATH` per trial) is already available to collect.
- `dev/eval/cumulative/runbook_vs_skill/phase2/probe_phase2.py` (imports `p1._real_vault_fingerprint`, 4 call sites across its own trial-running functions) — **fix**: same change, inherited automatically once `probe.py`'s function is fixed (it's imported, not copied).
- `dev/eval/isolation.py::vault_fingerprint`/`assert_vault_unchanged`, used as an end-of-run `__main__` bracket by 7 harnesses (`dev/eval/traps/{reasoning_eval,run,qanchor_eval,brun}.py`, `dev/eval/cumulative/endorse_cue/probe.py`, `dev/eval/cumulative/{please_step7_probe/run_probe,please_step3_probe/run_probe}.py`) — **fix the shared primitive once**, all 7 callers inherit it unchanged (none of these call sites pass trial envs to `assert_vault_unchanged` today, since it takes only a fingerprint; the new signature needs each caller to also pass its collected trial envs — a small threading change per caller, not a design change. Each of these 7 harnesses already builds one or more isolated trial envs via `isolated_env`/`engram_env`, so the evidence to pass exists at every site). Given these 7 run as straightforward batch scripts (no interactive orchestrator-side vault writes mid-run, unlike `probe.py`'s route-skill glances), the false-positive risk they carry today is lower than `probe.py`'s demonstrated case — but Joe's decision applies uniformly ("both guard implementations... find all callers and decide each"), so all get the same fix rather than leaving a second, differently-shaped guard in place.

**D10. The guard still fails loud on a genuine leak — two layers, not a weakening.** Layer 1 (cheap, always correct): assert every trial's recorded `ENGRAM_VAULT_PATH` was set and isolated — this alone proves no trial code path *could* have reached the real vault through the env-var-mediated route, which is how every call site spawns `engram`/`claude -p`. Layer 2 (defense in depth, matches the old guards' intent): scan any note newly present in the real vault for a trial dir/session id reference, catching a leak through a path the env vars don't mediate (the same "backstop for a path neither anticipates" rationale `isolation.py`'s own docstring already gives for why `assert_vault_unchanged` exists alongside `isolated_env`/`assert_isolated`).

### #755 — question_stop order-awareness + bisect-before-fix fixture

**D11. Thread the already-computed `end_state` boolean into `detect_question_stop`, short-circuiting to `False` when it's `True` — no new transcript-position tracking needed.** Verified: if a trial's final on-disk state already satisfies `done_when_checks.sh` (`end_state=True`), then by construction every mutation the task required already happened — and `detect_question_stop`'s existing scan already proves no mutation follows the last ambiguity-posing text. Combining these two facts: if `end_state` is `True` and no mutation follows the last ambiguity, that ambiguity cannot have blocked any required mutation — it is necessarily a trailing, already-irrelevant remark. So `question_stop` SHALL be `False` whenever `end_state` is `True`, full stop; no separate "did completion precede the ambiguity" position-tracking logic is needed, because `end_state=True` already proves it. Both call sites (`probe_phase2.py:1588` in `score_fields`, and `:2465` in the rescore path) need `end_state` computed *before* calling `detect_question_stop` — today the first call site computes `end_state` (line 1594) *after* `question_stop` (line 1588); reorder so `end_state` is available first, matching the second call site's existing order (there, `end_state` at line 2456 is already before `detect_question_stop` at line 2465, so only the first call site needs reordering). `detect_question_stop`'s signature becomes `detect_question_stop(events, task_key, end_state)` — a required third argument, not a default, so a future call site can't silently skip wiring it and regress to the current bug.

**D12. The `bisect-before-fix` fixture gets an `ISSUES.md` baked into the template directory (present from the initial commit), named in `task-prompt.txt`.** `dev/eval/cumulative/runbook_vs_skill/phase2/fixtures/fixture-repo-templates/bisect-before-fix-task/` is `cp -r`'d wholesale by `init_fixture_repo.sh` before the first commit, so adding `ISSUES.md` there makes it present at both the parent commit and final HEAD automatically — no init-script change needed. `task-prompt.txt` gains one sentence naming it as the place to file a follow-up issue, giving the runbook's step 6 ("file the pre-existing regression as its own separate issue") an actual local target to act on.

**D13. `done_when_checks.sh` is NOT updated to require an `ISSUES.md` entry; `steps.json` gets a new tracked (not pass/fail-gating) step instead.** `done_when_checks.sh` measures the fixture's core-task correctness (gate passes, `bar.py` fixed) **uniformly across all four arms** (R/F/S/N) for the harness's own cross-arm comparison — but only the runbook (arm R, when shim-following) is ever told about runbook 846's own `done_when` text requiring a filed issue. Making `done_when_checks.sh` fail on a missing `ISSUES.md` entry would fail arms that were never instructed to file one, corrupting the very cross-arm `end_state` comparison this harness exists to produce. Instead, add a `steps.json` step (e.g. step 8, gated `"after": 6`) detecting an `ISSUES.md` edit (`tool_path` on `ISSUES\.md$`, or a `bash_regex` for an append), scored into `followed_steps`/`followed_all` (which are already per-arm-relative, not a uniform pass/fail bar) — this answers "did a runbook-following trial actually comply with step 6" without biasing `end_state`.

## Risks / Trade-offs

- **[Risk] #710's future Go port inherits whatever test coverage these fixes get — thin coverage here becomes a silent gap there.** → Mitigation: every task below names a specific behavioral test (real invocation / real regex match / real fixture state), not a mock-only unit test, so the port has a concrete contract to satisfy; noted again in `tasks.md`'s own framing.
- **[Risk] D8/D9's `isolation.py` signature change (`assert_vault_unchanged` needs trial envs, not just a fingerprint) touches 7 call sites outside the two issues' "Affected files" lists.** → Mitigation: each is a small, mechanical threading change (pass the envs the caller already built); `tasks.md` gives each its own RED/GREEN step so a mistake in one doesn't block the others, and the old fingerprint-only path can stay as an internal implementation detail of the new primitive (layer 2 of D10) rather than being deleted, minimizing the diff's blast radius.
- **[Risk] D6's extra raise-on-missing-source fix to `probe.py` is not itself one of the five filed issues.** → Mitigation: flagged explicitly here and in `tasks.md` as a small, scoped, same-root-cause fix made while already touching the function for the docstring update — not separate scope creep, and reported as a decision rather than silently bundled.
- **[Trade-off] D11 makes `end_state` a required argument to `detect_question_stop`, a breaking signature change for any caller outside the two known ones.** → Mitigation: grepped — confirmed exactly two call sites exist in the whole repo; both are updated by this change.
